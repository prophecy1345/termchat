# AI-assisted security review, November 2026

Status: findings open. Reviewed commit: `f29f539` (0.5.1). Date: 2026-11-11.

**This is not an independent security audit.** It is a source review done by
an AI model (Claude Fable 5.2) at the maintainer's request. A model can miss
whole classes of bugs and cannot vouch for what it did not flag. termchat.app
stays experimental until people who are independent of the project audit it.

## Scope

Read in full: `crates/core`, `crates/proto`, `crates/engine`, `crates/relay`,
`docs/protocol.md`, `docs/threat-model.md`.

Read in part (searched for untrusted-text rendering, secret handling, file and
process use): `crates/client`, `crates/desktop`, `crates/ffi`, the Android
manifest and Kotlin sources, `deploy/`, `Dockerfile`, CI workflow headers.

Not reviewed: vodozemac, Arti, egui and every other dependency; the UI logic
of the three clients line by line; the install scripts, the release workflow
and the website; ADRs other than as context. Nothing was tested against the
live relay. No fuzzing was run. Timing claims (duress password) were read, not
measured.

One finding (1) was confirmed with a test. The others come from reading the
code.

## Findings

| # | Severity | Where | Summary |
|---|---|---|---|
| 1 | Medium | `core` `Client::decrypt` | The relay can replay messages of a session started on the fallback key |
| 2 | Medium | `engine` `on_frame` (`KeyCount`) | Only the relay decides when the fallback key rotates |
| 3 | Medium (relay availability) | `relay` `handshake` | A whole queue (10 MiB) is loaded into memory per connection |
| 4 | Low | `relay` `push::wake` | Push wake-ups have no global or per-host cap |

| 6 | Low | `data::write_atomic` | Predictable temp file next to a backup, opened with truncate |
| 7 | Low | `core`, `engine` | Plaintext and serialized key state leave unwiped copies in memory |
| 8 | Info | `Cargo.lock` | Two new RustSec advisories fail `cargo deny` |
| 9 | Info | `engine::relay` | The client accepts WebSocket messages far larger than the protocol allows |
| 10 | Info | various | Smaller notes |

### 1. Replay of pre-key messages on a fallback-key session (Medium)

Who: the relay operator, or whoever controls the relay.

`Client::decrypt` first tries the sessions it has. If a pre-key message has
the id of a known session but does not decrypt there (its message key was
already used), the loop moves on and the code falls through to
`create_inbound_session`. A one-time key is gone after first use, so that
fails. A fallback key is still in the account, so a second session with the
same id is created, the plaintext is decrypted again, and a fresh `SeqTracker`
accepts its `seq`.

Confirmed with this test (it fails on `f29f539`: both replays return `Ok`):

```rust
let mut alice = Client::default();
let mut bob = Client::default();
let fallback = bob.prekeys(0, true).fallback.unwrap();
alice.add_contact(&bob.identity()).unwrap();
bob.add_contact(&alice.identity()).unwrap();
let (a, b) = (alice.identity().ed25519, bob.identity().ed25519);
alice.start_session(&b, &fallback).unwrap();
let env = alice.encrypt(&b, text("pay 100")).unwrap();
assert!(bob.decrypt(&a, &env).is_ok());
assert!(bob.decrypt(&a, &env).is_err()); // fails: the replay is accepted
```

Effect: every message a sender wrote before the recipient's first reply (all
of them are pre-key messages) can be delivered again, any number of times, for
as long as the recipient holds that fallback key (the current one, or the
previous one for 15 days after rotation). The engine shows the copy as a new
message under "they restarted the conversation". The relay chooses when the
fallback key is handed out (see finding 2), so it can arrange this for any new
session.

The copy also becomes the recipient's active session. Its replies then go out
on a clone of the session's first state, which the peer has most likely moved
past; this part was not tested.

This contradicts threat-model item 5 ("forged, replayed or reordered
messages").

Not covered by the simple fix: a session that was pushed out by
`MAX_SESSIONS`, or removed with the contact, is no longer there to compare
ids with. Its pre-key messages replay the same way while the fallback key
lives. For a deleted contact this lets the relay bring a contact request back
with a public invite code.

Suggested fix (needs an ADR, rule 2):
- a pre-key message whose session id matches a known session and fails to
  decrypt there is an error, never a new session;
- keep the ids of inbound sessions created on a fallback key (per identity,
  bounded) until that fallback key is forgotten, and refuse to create them
  again.

### 2. Fallback key rotation depends on the relay (Medium)

`rotate = !published || (used && since.is_none())`, where `used` comes from
the relay's `KeyCount`. A relay that never reports `fallback_used` and always
hands out the fallback key (its signature is valid, the client cannot tell)
keeps one fallback key in use for good. Then every new session starts on the
same long-lived key: the first messages of each session, up to the recipient's
first reply, lose forward secrecy against a later compromise of that key, and
the replay window of finding 1 never closes.

Suggested fix (ADR): rotate the fallback key on the client's own clock as
well, for example weekly, whatever the relay reports.

### 3. The relay loads a whole queue into memory at login (Medium, availability)

`handshake` calls `db.queued(&key)` under the global lock and keeps every
envelope as a `ServerFrame` until it is written out. A queue may hold 10 MiB.
A client that authenticates and then does not read holds that memory until the
30-second write timeout. One IP may open 50 connections; the onion listener
allows 2000. Keys that write to each other fill each other's queues within the
documented limits, so an attacker can prepare this cheaply and repeat it on
every reconnect. On a small server this is enough to run out of memory.

Suggested fix: deliver the queue in pages (for example 50 envelopes), and read
the next page as acks arrive.

### 4. Push wake-ups are not capped overall (Low)

A wake-up is limited to one per 30 seconds per recipient key, but there is no
limit across keys or per destination host, and each one is a spawned task with
a TLS handshake. Someone with many keys can make the relay send a steady
stream of HTTPS requests to a host of their choice, from the relay's address,
and tie up the relay's own sockets. The address checks (public addresses only,
port 443, no redirects, connect to the checked address) are sound.

Suggested fix: a semaphore for concurrent wake-ups and a small per-host rate
limit.

### 5. File names of received documents (Low)

`check_file_name` rejects path separators, control and bidi characters, `.`
and `..`. It accepts:
- names that start with a dot. `save_new` never overwrites, but a contact's
  `.zshenv` or `.bash_profile` saved into the home folder (the folder is typed
  by the user; the default is `~/Downloads`) is run by the next shell if no
  such file existed;
- on Windows, `:` (writes an alternate data stream of another file), reserved
  device names (`CON`, `NUL`, ...), and trailing dots or spaces.

Suggested fix: on receipt or on save, refuse or prefix names that start with a
dot, and refuse `: * ? " < > |` and the reserved device names.

### 6. Temp file of `write_atomic` when writing a backup (Low)

A backup written to `dir/name` goes through `dir/name.tmp`, opened with
create and truncate. In a folder other users can write to (`/tmp`, a shared
mount), a planted symlink at that path makes the client overwrite the link's
target with ciphertext, and an unrelated `name.tmp` of the user's own is
silently replaced. The state folder itself is `0700`, so the state file is not
affected.

Suggested fix: create the temp file with `create_new` and a random suffix.

### 7. Unwiped copies of plaintext and key state in memory (Low)

The final buffers are wrapped in `Zeroizing`, but:
- `serde_json::to_vec` and `to_string` grow their buffer by reallocating;
  earlier, shorter copies (the pickled account with its private keys in
  `Client::state_json`, the message history in `Data::to_json`) are freed
  without being wiped;
- `Data::to_json` clones the whole `Data` and drops the clone unwiped;
- on lock, `Data` (all message text) is dropped unwiped.

The threat model already excludes malware and swap. The statement that locking
wipes keys from memory holds for vodozemac's own objects, not for these
intermediate copies. Either reduce the copies (serialize into a pre-sized
`Zeroizing` buffer, wipe `Msg` text on drop) or say so in the threat model.

### 8. New dependency advisories (Info)

`cargo deny check advisories` fails today on:
- RUSTSEC-2026-0459, `libsqlite3-sys 0.38.2` (bundled SQLite; needs a crafted
  database and `-wal` pair, and the relay opens only its own files);
- RUSTSEC-2026-0486, `rustix 1.1.5` (xattr functions, which termchat.app does
  not call).

Neither looks exploitable here, but the CI `deny` job will fail. Fix:
`rusqlite` 0.41 and `cargo update -p rustix`.

### 9. Client-side WebSocket limits (Info)

The relay caps messages at 64 KiB. The client connects with tungstenite's
defaults (messages up to 64 MiB), so a hostile relay can make it buffer that
much before `ServerFrame::decode` rejects the frame. Set `max_message_size` to
`MAX_FRAME_BYTES` on the client too.

### 10. Smaller notes (Info)

- `check_nickname` rejects control characters but not bidi overrides, unlike
  `check_file_name`. All three clients strip them when drawing, so this is a
  consistency gap only.
- A signed prekey says neither "one-time" nor "fallback" and carries no date.
  The relay can hand out an already used one-time key (the first messages are
  then undecryptable: a drop, which the relay can do anyway).
- `Unregister` followed by a new login with the same key resets that key's
  in-memory limits and report count. It costs one registration, the same as a
  new key.
- After a relay restart every pair counts as strangers until the recipient
  writes again, so a document sent to an offline contact can hit `QueueFull`.
- `deploy/docker-compose.yml` uses `caddy:2` without a digest, unlike the
  relay's own base image.

## Checked, no problem found

- Identity card: the Curve25519 key is bound to the Ed25519 key; the check
  runs for invites, contact requests and relay login.
- Relay login: fresh nonce per connection, host in the signed text, distinct
  signature contexts for identity, prekeys and login.
- A stranger's first message: sender, identity keys and signature are all
  checked against the Olm session; invite codes are compared in constant time
  and one-time codes are spent.
- Inner message: sender and recipient inside the ciphertext are checked.
- State file: header as associated data, two look-alike slots, both slots
  derived on every path, limits on Argon2 parameters from the file.
- Decoders: size checks before allocation, canonical encoding enforced.
- Text from peers is stripped of control and bidi characters where it is drawn
  (TUI, desktop, FFI); pasted text cannot act as keys.
- `ws://` only for loopback and onion hosts; with Tor on there is no direct
  fallback.
- Relay: SQL is parameterized, only the recipient can ack, the push endpoint
  checks hold, nothing about IPs or contents is logged.
- Android: no system backup or device transfer, no exported components beyond
  the launcher, `FLAG_SECURE` in release builds.
- CI actions are pinned by commit.

# Протокол termchat, версия 1

Статус: принято (M0, 2026-10-15). Изменения формата повышают `version`. English: [protocol.md](protocol.md).

## 1. Слои

1. **Транспорт:** WebSocket поверх TLS (`wss://`). TLS терминирует reverse proxy, relay видит обычный WS. Каждое сообщение — один бинарный WS-фрейм. Текстовые фреймы — ошибка протокола, соединение закрывается.
2. **Фреймы:** перечисления `ClientFrame` и `ServerFrame`, кодируются `postcard`. Используются для регистрации, ключей, отправки и доставки.
3. **Конверт:** то, что relay пересылает от клиента к клиенту. Тело конверта — сообщение Olm.
4. **Внутреннее сообщение:** открытый текст внутри Olm, с padding.

Все числа — в кодировке postcard (varint). Ключи Ed25519 и Curve25519 — 32 байта, подписи Ed25519 — 64 байта.

Принимается только каноническая кодировка: postcard допускает избыточно длинные varint, поэтому декодер кодирует значение заново и сравнивает с входом (найдено fuzz-тестом в M1).

**Identity** — самоудостоверяющая карточка пользователя:

```
Identity { ed25519: [u8; 32], curve25519: [u8; 32], signature: [u8; 64] }
```

`signature` — подпись Ed25519 над `"termchat-id-v1" || curve25519`. Связывает ключ обмена с ключом подписи. Без неё подмена `curve25519` в приглашении не ловилась бы сверкой отпечатка (отпечаток считается только по Ed25519), и подменивший мог бы читать сообщения. Клиент принимает контакт только после проверки подписи.

## 2. Версия

Первый фрейм клиента — `Hello { version: u16 }`. Сейчас `version = 1`. Если relay не поддерживает версию, он отвечает `Error { code: UnsupportedVersion }` и закрывает соединение. Конверт тоже несёт `version`, чтобы клиенты разных версий могли понять друг друга или явно отказать.

## 3. Регистрация (challenge-response)

```
C -> R  Hello { version }
R -> C  Challenge { nonce: [u8; 32] }
C -> R  Auth { identity: Identity, signature }
R -> C  AuthOk | Error { code }
```

`signature` — подпись Ed25519 над байтами:

```
"termchat-auth-v1" || relay_host || nonce
```

- `relay_host` из URL relay (например `relay.example.org` или `xxxx.onion`) не даёт переиспользовать подпись на другом relay. Relay принимает любой из своих адресов (`--host` можно указать несколько раз).
- Связь ключа обмена с ключом подписи даёт подпись внутри `identity`; relay её проверяет.
- Nonce одноразовый и привязан к соединению; на весь обмен до `Auth` даётся 10 секунд (`auth_timeout`).

До `AuthOk` relay принимает только `Hello` и `Auth`.

## 4. Ключи (prekeys)

```
C -> R  PublishKeys { one_time: Vec<SignedKey>, fallback: Option<SignedKey> }
C -> R  ClaimKey { target: ed25519 }
R -> C  ClaimedKey { target, key: SignedKey } | Error { code: NoKeys }
R -> C  KeyCount { one_time_left: u32, fallback_used: bool }
```

- `KeyCount` приходит сразу после `AuthOk`, в ответ на `PublishKeys` и владельцу ключей, когда кто-то забрал его ключ (если он онлайн).
- `fallback_used = true`: relay выдал fallback key, клиент ротирует его (ADR-002).
- Ошибка на `ClaimKey` приходит с `client_id: None`; клиент запрашивает ключи по одному.
- Сверх лимита `ClaimKey` к одной цели relay выдаёт только fallback key, one-time keys не тратятся.

`SignedKey { key: [u8; 32], signature: [u8; 64] }`. Подпись Ed25519 владельца над `"termchat-otk-v1" || key`. Отдельный id не нужен: vodozemac находит one-time key по публичной части. Клиент, получивший ключ, проверяет подпись ключом `target`, поэтому relay не может подсунуть свой ключ.

Relay выдаёт one-time key один раз и удаляет. Если они кончились, выдаёт fallback key. Параметры (сколько публиковать, когда пополнять) — в ADR-002.

## 5. Отправка и доставка

```
C -> R  Send { client_id: u64, envelope: Envelope }
R -> C  Accepted { client_id } | Error { client_id, code }
R -> C  Deliver { relay_id: u64, sender: ed25519, envelope: Envelope }
C -> R  Ack { relay_id }
C -> R  Report { sender: ed25519, text: String }   // ADR-006, text до 16000 байт
R -> C  Reported                                  // одинаковый ответ на любом пути
```

- Relay держит конверт в очереди получателя, пока тот не пришлёт `Ack`. Неподтверждённые конверты приходят снова при каждом подключении. В M2 очередь в памяти и теряется при перезапуске relay; в M5 она переезжает в SQLite и получает TTL.
- `Accepted` означает, что relay принял конверт. В клиенте это «доставлено на сервер». E2E-квитанций о прочтении нет.
- `sender` в `Deliver` ставит relay по аутентифицированному соединению. Клиент не доверяет этому полю: настоящий отправитель подтверждается расшифровкой и проверкой внутреннего сообщения (раздел 7).
- `Ack` разрешает relay удалить конверт (важно с M5, когда появляется очередь).

## 6. Конверт

```
Envelope {
    version: u16,
    recipient: [u8; 32],      // ed25519 получателя
    olm_type: u8,             // 0 = pre-key, 1 = normal
    body: Vec<u8>,            // шифртекст Olm
}
```

Поля отправителя нет: так в будущем можно добавить sealed sender, не меняя формат.

## 7. Внутреннее сообщение

Открытый текст до шифрования Olm:

```
Inner {
    sender: [u8; 32],         // ed25519 отправителя
    recipient: [u8; 32],      // ed25519 получателя
    seq: u64,                 // номер сообщения в направлении sender -> recipient, с 1
    body: Body,
}

Body =
    ContactRequest { identity: Identity, nickname: String, note: String }  // первое сообщение незнакомцу
  | ContactAccept { nickname: String }
  | Text { sent_at: u64, expires_in: Option<u32>, text: String }
```

Лимиты: `text` до 16000 байт, `nickname` до 64 байт, `note` до 256 байт.

Проверки при получении:
1. `recipient` совпадает со своим ключом.
2. `sender` совпадает с ключом, к которому привязана сессия Olm. Для pre-key сообщения от контакта: Curve25519 из сообщения совпадает с `curve25519` из его проверенной `Identity`.
3. Pre-key сообщение от незнакомца принимается, только если это `ContactRequest`, его `identity.ed25519` равен `sender`, `identity.curve25519` равен Curve25519 из сообщения и подпись `identity` верна. Такой отправитель попадает в «запросы».
4. Иначе сообщение отбрасывается.

Никнейм — единственное, что собеседник узнаёт о человеке. Он передаётся только здесь, внутри шифртекста: до 64 байт UTF-8, не пустой, без управляющих символов (иначе собеседник мог бы послать escape-последовательность в чужой терминал). Получатель хранит его в своём зашифрованном файле. Других полей о человеке в протоколе нет.

Нумерация (`seq`):
- Счётчик свой у каждой сессии Olm и каждого направления, начинается с 1. Новая сессия (в том числе после восстановления из копии) начинает с 1.
- Отправитель увеличивает `seq` на 1 для каждого сообщения и хранит счётчик в состоянии сессии. Повторная отправка того же сообщения использует тот же `seq`.
- Получатель хранит для сессии последний `seq` и множество пропущенных номеров.
  - `seq` больше последнего: принять. Номера между ними добавить в пропущенные и показать «пропущено N сообщений».
  - `seq` в множестве пропущенных: принять (пришло не по порядку), убрать из множества, обновить предупреждение.
  - иначе: дубликат, отбросить.
- `seq` лежит внутри шифртекста, relay его не видит и подделать не может.
- Пропуск, который не закрылся за TTL очереди relay, считается потерей. Множество пропущенных ограничено 1000 номерами, номера сверх лимита считаются в счётчик потерь. Olm (vodozemac 0.11) хранит не больше 40 ключей пропущенных сообщений на цепочку и допускает разрыв до 2000: пропущенное сообщение старше этого уже не расшифровать, и оно остаётся потерей.
- Ограничение: если relay выбросил **последние** сообщения, а новых нет, пропуск не виден. Его покажет следующее сообщение собеседника.

Сообщения от ключей, которых нет в контактах, показываются только в «запросах». Классификацию делает клиент, relay не знает список контактов. До принятия запроса (ADR-007): его `Text` не показываются, клиент хранит не больше 5 и показывает их после принятия; ник может обновить только новый `ContactRequest`, после принятия ник из сети не меняется; ожидающих запросов не больше 50; отклонённые ключи клиент запоминает и их сообщения не расшифровывает.

## 8. Padding

Сериализованный `Inner` дополняется до ближайшего бакета: `0x80`, затем нули (ISO/IEC 7816-4). Бакеты: **512, 4096, 16384 байт**. Больше 16384 — ошибка `TooLarge`.

- Лимит `text`: **16000 байт UTF-8** (~8000 кириллических или ~16000 латинских символов). Лимит в байтах, а не в символах: так размер предсказуем при любом алфавите.
- Служебные сообщения (`ContactRequest`, `ContactAccept`) дополняются так же и неотличимы от коротких текстовых.
- Мало бакетов — меньше утечка длины. Один фиксированный размер не выбран: он раздувает очередь relay в ~30 раз.

## 9. Строка-приглашение

```
termchat:<base64url(postcard(Invite))>

Invite { version: u16, relay_url: String, onion_url: Option<String>, identity: Identity }
```

Fallback key в приглашение не кладётся: он ротируется и быстро устареет. One-time key берётся через `ClaimKey`, подпись защищает от подмены.

Короткого варианта для ручного ввода нет: строку копируют, а короткий код потребовал бы хранить на relay связь «код → ключи». Позже: QR-код в терминале.

## 10. Отпечаток

Схема как в Signal: у каждого ключа свой отпечаток, номер безопасности — оба отпечатка подряд.

- **Отпечаток ключа**, 30 цифр: `h = SHA-512("termchat-fp-v1" || ed25519)`. Первые 30 байт `h` делятся на 6 кусков по 5 байт. Каждый кусок читается как big-endian число и берётся по модулю 100000, получается группа из 5 цифр.
- **Номер безопасности** пары, 60 цифр: отпечатки обоих ключей в порядке сортировки ключей, 12 групп по 5 цифр. Одинаковый у обоих собеседников.

Почему не хеш от пары ключей: при MITM атакующий выбирает оба своих ключа и ищет совпадение номеров атакой «дней рождения» (~2^(n/2) попыток). С отдельными отпечатками ему нужен ключ с таким же отпечатком, как у конкретного человека: ~2^99 попыток.

## 11. Лимиты (значения по умолчанию, настраиваются в relay)

| Что | Значение |
|---|---|
| Размер WS-фрейма | 64 KiB |
| `body` конверта | 16384 + накладные расходы Olm, не больше 20 KiB |
| `Send` от одного ключа | token bucket: 30 подряд, затем 1 в 2 секунды |
| Новых получателей от одного ключа | 20 в сутки |
| Соединений с одного IP | 50 (CGNAT: много людей за одним IP) |
| Любых кадров после `Auth`, на ключ | token bucket: 2000 залпом (вся очередь, подтверждаемая после переподключения), далее 20 в секунду; сверх того соединение закрывается |
| Новых регистраций с одного IP | 20 в час (через onion: общий бюджет 200 в час, ADR-004) |
| One-time keys на ключ | клиент держит на relay 50 (`Account::max_number_of_one_time_keys()`), relay хранит не больше 100 новейших |
| `PublishKeys` от одного ключа | 30 в час |
| `ClaimKey` от одного ключа | 30 в час |
| `ClaimKey` к одной цели от всех | 100 в сутки (сверх лимита выдаётся только fallback key) |
| Время на аутентификацию | 10 секунд после подключения |
| Запись клиенту | 30 секунд: кто не читает, тот отключается |
| Очередь на получателя (M5) | 1000 конвертов и 10 MiB, TTL 14 дней |
| Доля незнакомца в очереди (ADR-007) | 20 конвертов и 256 KiB от отправителя, которому получатель ни разу не писал |
| Переполненный канал к онлайн-клиенту | relay рвёт соединение, клиент переподключается и получает очередь (ADR-007) |

Счётчики живут только в памяти.

Подключения через Tor приходят с общих IP выходных узлов, поэтому лимиты по IP их несправедливо задевают. Для них relay публикует onion-адрес: у onion-подключений лимитов по IP нет, работают лимиты по ключу и общий бюджет onion-порта. Свой proof-of-work не реализован: его даёт Tor для onion-сервисов (ADR-004).

## 12. Коды ошибок

`UnsupportedVersion`, `Malformed`, `TooLarge`, `NotAuthenticated`, `BadSignature`, `ChallengeExpired`, `RateLimited`, `NoKeys`, `UnknownRecipient`, `QueueFull`, `Banned`, `Internal`.

Ошибка с конкретным `client_id` не рвёт соединение. `Malformed`, `BadSignature`, `NotAuthenticated` закрывают соединение.

## 13. Keepalive и реконнект

- Ping от relay каждые 30 секунд. Нет pong за 60 секунд — соединение закрывается.
- Клиент переподключается с экспоненциальной задержкой и случайным разбросом: от 1 до 60 секунд.
- Неподтверждённые `Send` клиент повторяет после повторной аутентификации. Дубликаты отсеивает получатель по `seq`.

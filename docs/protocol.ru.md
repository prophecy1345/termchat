# Протокол termchat.app, версия 1

Статус: принято (M0, 2026-10-15); версия 2, анонимные очереди, принята 2026-11-16 (ADR-023). Изменения формата повышают `version`. English: [protocol.md](protocol.md).

## 1. Слои

1. **Транспорт:** WebSocket поверх TLS (`wss://`). TLS терминирует reverse proxy, relay видит обычный WS. Каждое сообщение — один бинарный WS-фрейм. Текстовые фреймы — ошибка протокола, соединение закрывается.
2. **Фреймы:** перечисления `ClientFrame` и `ServerFrame`, кодируются `postcard`. Используются для очередей, ключей, отправки и доставки.
3. **Конверт:** то, что relay пересылает от клиента к клиенту. Тело конверта — сообщение Olm.
4. **Внутреннее сообщение:** открытый текст внутри Olm, с padding.

Все числа — в кодировке postcard (varint). Ключи Ed25519 и Curve25519 — 32 байта, подписи Ed25519 — 64 байта.

Принимается только каноническая кодировка: postcard допускает избыточно длинные varint, поэтому декодер кодирует значение заново и сравнивает с входом (найдено fuzz-тестом в M1).

**Identity** — самоудостоверяющая карточка пользователя:

```
Identity { ed25519: [u8; 32], curve25519: [u8; 32], signature: [u8; 64] }
```

`signature` — подпись Ed25519 над `"termchat-id-v1" || curve25519`. Связывает ключ обмена с ключом подписи. Без неё подмена `curve25519` в приглашении не ловилась бы сверкой отпечатка (отпечаток считается только по Ed25519), и подменивший мог бы читать сообщения. Клиент принимает контакт только после проверки подписи.

## 2. Версия

Первый фрейм клиента в каждом соединении — `Hello { version: u16 }`. Сейчас `version = 2` (ADR-023). Если relay принимает версию, он ничего не отвечает. Иначе отвечает `Error { code: UnsupportedVersion }` и закрывает соединение. `Hello` остаётся вариантом 0, а `Error` — вариантом 7 своих перечислений, как в версии 1, поэтому клиент версии 1 может прочитать этот отказ. Конверт тоже несёт `version`.

В версии 1 были аккаунты: подписанный вход и конверты, адресованные ключам личности. Она не поддерживается; relay версии 2 при обновлении стирает свои данные.

Ответ relay на HTTP upgrade несёт `x-termchat-version: X.Y.Z` — версию программы relay. Клиенты используют её только чтобы сообщить, что вышел более новый termchat.app (ADR-010); в протоколе она не участвует.

## 3. Очереди (ADR-023)

Пользователей relay не знает. Он знает очереди:

```
C -> R  CreateQueue
R -> C  QueueCreated { recv_id: [u8; 16], send_id: [u8; 16], token: [u8; 32] }
C -> R  Subscribe { recv_id, token }
R -> C  Subscribed { recv_id }
C -> R  DeleteQueue { recv_id, token }
R -> C  QueueDeleted { recv_id }
```

- Все три значения relay выбирает случайно. Он хранит `recv_id`, `send_id` и SHA-256 от `token` и сравнивает хеши за постоянное время.
- `recv_id` и `token` остаются у владельца очереди: по ним её читают и удаляют. `send_id` — адрес, по которому в неё пишут; другим он попадает только внутри Olm (`QueueOffer`, раздел 7) или в приглашении (раздел 9).
- Неверный токен и неизвестная очередь получают один ответ: `UnknownQueue`.
- После `Subscribed` relay присылает сохранённые конверты очереди, затем `KeyCount`, затем новые конверты по мере прихода. Более новая подписка на ту же очередь забирает её себе.
- У каждой личности есть очередь приглашения, куда пишут незнакомцы. У каждого контакта своя очередь, в которую пишет только он. Блокировка контакта удаляет его очередь.
- Клиент держит отдельное соединение на каждую очередь, которую читает, чтобы relay не мог связать очереди по соединению (ADR-023, раздел 7); с Tor — каждое по своей цепочке.
- Очереди, которыми не пользовались 90 дней, удаляются.

## 4. Ключи (prekeys)

```
C -> R  PublishKeys { recv_id, token, one_time: Vec<SignedKey>, fallback: Option<SignedKey> }
C -> R  ClaimKey { send_id }
R -> C  ClaimedKey { send_id, key: SignedKey } | Error { code: NoKeys }
R -> C  KeyCount { recv_id, one_time_left: u32, fallback_used: bool }
```

- На очереди приглашения лежат одноразовые ключи личности и её fallback key. На очереди контакта — два одноразовых ключа и никакого fallback key: так контакт может начать новую сессию (после восстановления из бэкапа), а relay не может связать очереди по общему ключу (ADR-023, поправка).
- `KeyCount` приходит подписчику очереди после `Subscribed`, в ответ на `PublishKeys` и когда кто-то забрал один из её ключей.
- `fallback_used = true`: relay выдал fallback key, клиент ротирует его (ADR-002). Fallback key старше 7 дней клиент ротирует и сам, по своим часам, что бы ни сообщал relay (ADR-019).
- Ошибка на `ClaimKey` приходит с `client_id: None`; клиент запрашивает ключи по одному.
- Сверх лимита `ClaimKey` к одной очереди relay выдаёт только fallback key, one-time keys не тратятся.

`SignedKey { key: [u8; 32], signature: [u8; 64] }`. Подпись Ed25519 владельца над `"termchat-otk-v1" || key`. Отдельный id не нужен: vodozemac находит one-time key по публичной части. Клиент, получивший ключ, проверяет подпись ключом личности из приглашения, поэтому relay не может подсунуть свой ключ.

Relay выдаёт one-time key один раз и удаляет. Если они кончились, выдаёт fallback key, если он есть у очереди. Параметры (сколько публиковать, когда пополнять) — в ADR-002.

## 5. Отправка и доставка

```
C -> R  Send { client_id: u64, send_id, envelope: Envelope }
R -> C  Accepted { client_id } | Error { client_id, code }
R -> C  Deliver { recv_id, relay_id: u64, envelope: Envelope }
C -> R  Ack { recv_id, relay_id }
C -> R  Report { recv_id, token, text: String }  // ADR-006, text до 16000 байт
R -> C  Reported                                 // одинаковый ответ на любом пути
C -> R  SetPush { recv_id, token, endpoint: Option<String> }  // ADR-012
R -> C  PushSet                                  // или Error { Malformed } для плохого URL
```

- Для `Send` вход не нужен: право писать даёт знание `send_id`.
- Relay держит конверт в очереди, пока её подписчик не пришлёт `Ack`. Неподтверждённые конверты приходят снова при каждой подписке. Очередь лежит в SQLite и имеет TTL (ADR-005). Подтвердить может только подписчик очереди.
- `Accepted` означает, что relay принял конверт. В клиенте это «доставлено на сервер». E2E-квитанций о прочтении нет.
- `Deliver` не называет отправителя: relay его не знает. Клиент узнаёт контакт по очереди и подтверждает его расшифровкой и проверкой внутреннего сообщения (раздел 7). Из очереди приглашения он читает только pre-key сообщения.
- `Report` отправляет раскрытый текст в журнал оператора. Забанить кого-либо relay не может: он не знает ключей (ADR-023, раздел 6).
- `SetPush` сохраняет у очереди endpoint UnifiedPush (ADR-012), `None` забывает его: URL `https` на порту 443, до 512 байт. Когда конверт ставится в очередь, которую никто не читает или чей читатель спит, relay делает POST с пустым телом на endpoint — не чаще раза в 30 секунд и только на публичные адреса. У каждой очереди свой endpoint, иначе relay связал бы очереди по нему.
- Удаление аккаунта шлёт прощания, затем удаляет все очереди (ADR-009).

### Очереди групп (ADR-027)

```
C -> R  CreateGroup                                   R -> C  GroupCreated { group_id, send_id, token }
C -> R  AddReader { group_id, token }                 R -> C  ReaderAdded { group_id, recv_id, send_id, token }
C -> R  RemoveReader { group_id, token, recv_id }     R -> C  ReaderRemoved { recv_id }
C -> R  DeleteGroup { group_id, token }               R -> C  GroupDeleted { group_id }
C -> R  RemoveReaderAt { group_id, token, send_id }   R -> C  ReaderRemoved { recv_id }
```

- У очереди группы есть `group_id` и токен администратора и `send_id` для участников. `Send` в неё кладёт копию конверта в очередь каждого читателя; переполненная очередь одного читателя не задерживает остальных.
- Читатель — обычная очередь (`Subscribe`, `Ack`, `PublishKeys`, `SetPush`, как выше), созданная администратором для одного участника. Её собственный `send_id` доходит только до этого участника: через него участники передают друг другу ключи Megolm по Olm.
- Не больше 32 читателей. Создание группы или читателя расходует тот же бюджет, что `CreateQueue`. Неверный токен или `recv_id`, который не читатель этой группы, получают `UnknownQueue`.
- `RemoveReaderAt` (ADR-042) — то же, что `RemoveReader`, но читатель назван своим `send_id` и ищется только среди читателей этой группы.
- `RemoveReader` удаляет очередь этого читателя; `DeleteGroup` удаляет группу и всех читателей. Группа, которой не пользовались 90 дней, удаляется, если за это время не появлялся и ни один её читатель.

## 6. Конверт

```
Envelope {
    version: u16,
    olm_type: u8,             // 0 = pre-key, 1 = normal
    body: Vec<u8>,            // шифртекст Olm
}
```

Ни отправителя, ни получателя: relay адресует очередь, а оба имени лежат внутри шифртекста (раздел 7).

## 7. Внутреннее сообщение

Открытый текст до шифрования Olm:

```
Inner {
    sender: [u8; 32],         // ed25519 отправителя
    recipient: [u8; 32],      // ed25519 получателя
    seq: u64,                 // номер сообщения в направлении sender -> recipient, с 1
    body: Body,
}

Body =
    ContactRequest { identity: Identity, nickname: String, note: String }  // первое сообщение незнакомцу
  | ContactAccept { nickname: String }
  | Text { sent_at: u64, expires_in: Option<u32>, text: String }
  | Goodbye                                                                // ADR-009: отправитель стёр аккаунт
  | ContactRequestV2 { identity: Identity, nickname: String, note: String, code: [u8; 16] }  // ADR-013
  | File { id: u32, name: String, size: u32, index: u16, expires_in: Option<u32>, data: Vec<u8> }  // ADR-017
  | QueueOffer { relay_url: String, onion_url: Option<String>, send_id: [u8; 16] }  // ADR-023: пиши мне сюда
```

Следующие виды идут в таком порядке, каждый описан в своём ADR: `Message`, `Edit`, `Delete`, `React`, `Understands` (ADR-025); `GroupInvite`, `GroupJoin`, `GroupKey`, `GroupRoster`, `GroupLeave`, `GroupMove` (ADR-027); виды устройств из раздела 9 (ADR-028); `Copy` (ADR-030); и `Heartbeat { sent_at: u64 }` (ADR-031), который идёт только напрямую между основными устройствами, никогда внутри группы или `Copy`, и не показывается в чате. Незнакомый вид учитывается в `seq` и пропускается.

Лимиты: `text` до 16000 байт, `nickname` до 64 байт, `note` до 256 байт.

`File` — один кусок документа размером `size` байт, не больше 1 МиБ (ADR-017). Кусок `index` содержит байты начиная с `index * 16000`: ровно 16000 или остаток в последнем куске. `name` — от 1 до 255 байт, без управляющих и bidi-символов, без `/`, `\` и NUL, не `.` и не `..`. Получатель принимает куски одного файла строго по порядку, только от принятых контактов, и бросает передачу при пропуске.

Документ больше 1 МиБ, до 25 МиБ, сначала предлагается (ADR-043): `FileOffer { id, name, size, expires_in }`; байты идут только после `FileWant { id }` от получателя, частями `FilePart { id, index, data }` по 64000 байт (остаток в последней), по порядку. Получатель отвечает `FileAck { id, next }` каждые 16 частей и после последней; у отправителя не больше 64 неподтверждённых частей. `FileStop { id }` от любой стороны завершает передачу. Только между принятыми контактами с `Understands` уровня 7, никогда в группе и в `Copy`.

`QueueOffer` передаёт контакту `send_id` очереди, которую мы для него создали; URL подчиняются лимитам приглашения и должны быть `wss://` (или `ws://` для onion-адреса). Дальше контакт пишет туда. Знакомство идёт в таком порядке:

1. Тот, кто просит контакт, пишет в очередь приглашения: `ContactRequestV2`, затем `QueueOffer` со своей очередью.
2. Принимающий пишет в эту очередь: сначала свой `QueueOffer`, потом `ContactAccept`. Так у просившего адрес появляется раньше, чем он сможет отправить обычное сообщение.

Уже знакомый контакт, который просит снова (новое устройство или переход с версии 1), присоединяется к своему контакту: ник, история и отпечаток сохраняются.

Проверки при получении:
1. `recipient` совпадает со своим ключом.
2. `sender` совпадает с контактом, в чью очередь пришёл конверт, и с ключом, к которому привязана сессия Olm. Для pre-key сообщения от контакта: Curve25519 из сообщения совпадает с `curve25519` из его проверенной `Identity`. В очереди приглашения отправитель — контакт с этим Curve25519; незнакомец там не может назваться нашим контактом.
3. Pre-key сообщение от незнакомца принимается, только если это `ContactRequest` или `ContactRequestV2` с действующим кодом приглашения (раздел 9), его `identity.ed25519` равен `sender`, `identity.curve25519` равен Curve25519 из сообщения и подпись `identity` верна. Такой отправитель попадает в «запросы».
4. Иначе сообщение отбрасывается.
5. Pre-key сообщение никогда не создаёт одну и ту же сессию дважды (ADR-019). Отбрасывается сообщение, у которого id сессии совпадает с уже имеющейся сессией контакта и которое эта сессия не может расшифровать. Отбрасывается и сообщение, id сессии которого есть в списке входящих сессий, созданных этой личностью. В списке не больше 200 id на отправителя и 10 000 всего; id удаляется, когда забывается fallback key, которым он мог быть создан. Без этого pre-key сообщение, отправленное на fallback key (он остаётся в аккаунте), можно было бы доставить и прочитать повторно.

Никнейм — единственное, что собеседник узнаёт о человеке. Он передаётся только здесь, внутри шифртекста: до 64 байт UTF-8, не пустой, без управляющих символов (иначе собеседник мог бы послать escape-последовательность в чужой терминал). Получатель хранит его в своём зашифрованном файле. Других полей о человеке в протоколе нет.

Нумерация (`seq`):
- Счётчик свой у каждой сессии Olm и каждого направления, начинается с 1. Новая сессия (в том числе после восстановления из копии) начинает с 1.
- Отправитель увеличивает `seq` на 1 для каждого сообщения и хранит счётчик в состоянии сессии. Повторная отправка того же сообщения использует тот же `seq`.
- Получатель хранит для сессии последний `seq` и множество пропущенных номеров.
  - `seq` больше последнего: принять. Номера между ними добавить в пропущенные и показать «пропущено N сообщений».
  - `seq` в множестве пропущенных: принять (пришло не по порядку), убрать из множества, обновить предупреждение.
  - иначе: дубликат, отбросить.
- `seq` лежит внутри шифртекста, relay его не видит и подделать не может.
- Пропуск, который не закрылся за TTL очереди relay, считается потерей. Множество пропущенных ограничено 1000 номерами, номера сверх лимита считаются в счётчик потерь. Olm (vodozemac 0.11) хранит не больше 40 ключей пропущенных сообщений на цепочку и допускает разрыв до 2000: пропущенное сообщение старше этого уже не расшифровать, и оно остаётся потерей.
- Ограничение: если relay выбросил **последние** сообщения, а новых нет, пропуск не виден. Его покажет следующее сообщение собеседника.

Сообщения от ключей, которых нет в контактах, показываются только в «запросах». Классификацию делает клиент, relay не знает список контактов. До принятия запроса (ADR-007): его `Text` не показываются, клиент хранит не больше 5 и показывает их после принятия; ник может обновить только новый `ContactRequest`, после принятия ник из сети не меняется; ожидающих запросов не больше 50; отклонённые ключи клиент запоминает и их сообщения не расшифровывает.

## 8. Padding

Сериализованный `Inner` дополняется до ближайшего бакета: `0x80`, затем нули (ISO/IEC 7816-4). Бакеты: **512, 4096, 16384 байт**. Больше 16384 — ошибка `TooLarge`. Четвёртый бакет, **65536 байт**, несёт только `FilePart` (ADR-043); всё остальное в нём отклоняется.

- Лимит `text`: **16000 байт UTF-8** (~8000 кириллических или ~16000 латинских символов). Лимит в байтах, а не в символах: так размер предсказуем при любом алфавите.
- Служебные сообщения (`ContactRequest`, `ContactAccept`) дополняются так же и неотличимы от коротких текстовых.
- Мало бакетов — меньше утечка длины. Один фиксированный размер не выбран: он раздувает очередь relay в ~30 раз.

## 9. Строка-приглашение

```
termchat:<base64url(postcard(Invite))>

Invite { version: 3, relay_url: String, onion_url: Option<String>, identity: Identity, queue: [u8; 16], code: [u8; 16] }
```

`queue` — `send_id` очереди приглашения владельца (ADR-023). Приглашения версий 1 и 2 называли только личность и отклоняются с `UnsupportedVersion`; клиент просит новое. Relay может быть не тот, что у владельца.

`code` — случайный. Запрос повторяет его в `ContactRequestV2`. Клиент владельца пускает незнакомца только с действующим кодом: одноразовый тратится при получении, публичный работает, пока его не обновят. Всё остальное молча отбрасывается. Relay кода не видит (ADR-013).

Fallback key в приглашение не кладётся: он ротируется и быстро устареет. One-time key берётся через `ClaimKey { send_id: queue }`, подпись защищает от подмены.

Короткого варианта для ручного ввода нет: строку копируют, а короткий код потребовал бы хранить на relay связь «код → ключи». Позже: QR-код в терминале.


### Устройства (ADR-028)

Новое устройство просит привязать его кодом привязки: те же поля `Invite`
под своим префиксом, чтобы одно нельзя было принять за другое.

```
termchat-link:<base64url(postcard(Invite))>
```

Основное отвечает в эту очередь приглашений pre-key сообщением с телом
`DeviceLink { code, identity }`, которое принимается как запрос контакта (код
должен совпасть с кодом из кода привязки, `identity` должна связывать ключи
отправителя). Затем оба экрана показывают отпечаток личности; когда человек
подтверждает на обоих, новое устройство отправляет `DeviceLinked`, и основное
подписывает новый список.

```
DeviceList { identity: [u8; 32], no: u64, devices: Vec<Device>, signature: [u8; 64] }
Device { ed25519: [u8; 32], curve25519: [u8; 32] }
DeviceQueue { device: [u8; 32], relay_url: String, onion_url: Option<String>, send_id: [u8; 16] }

Body += DeviceLink { code: [u8; 16], identity: Identity }
      | DeviceLinked
      | LinkedContact { contact: LinkedContact }   // основное -> новому, по одному контакту
      | OwnDevices { list: DeviceList, labels: Vec<([u8; 32], String)>, nickname: String }  // только своим
      | Devices { list: DeviceList, queues: Vec<DeviceQueue> }                             // контактам
      | OwnQueue { contact: [u8; 32], queue: DeviceQueue }                                 // только своим
      | SiblingQueue { device: [u8; 32], queue: DeviceQueue }   // привязанное -> основное -> привязанное
      | GroupDevices { group: [u8; 16], member: [u8; 32], list: DeviceList,
                       readers: Vec<([u8; 32], [u8; 16])> }   // администратор -> группе, внутри Megolm
      | OwnGroupJoin { group: [u8; 16] }                       // только своим
```

Привязанные устройства знакомятся через основное: каждое создаёт очередь для
другого и отправляет её адрес в `SiblingQueue` основному, а то проверяет, что
оба в списке, и передаёт дальше.

В группах каждое устройство читает очередь группы. Состав называет личности
с читателем их основного устройства; `GroupDevices` добавляет список
участника, подписанный им самим, и читателя каждого привязанного устройства.
У каждого устройства своя сессия Megolm, оно делится ею со всеми устройствами
и подписывает сообщения собой; сообщение засчитывается участнику, в
проверенном списке которого есть это устройство. Администратор следит за
списками участников по их `Devices`: новое устройство получает читателя и
приглашение, а удалённое заставляет группу переехать без него.

Список подписан ключом личности над `"termchat-devices-v1" ||
postcard(identity, no, devices)`. Первое устройство — основное: его ключ и есть
личность. Не больше 4 устройств, без повторов ключа. Получатель принимает
список только от этой личности, с верной подписью и номером не ниже
известного, и забывает сессии устройств, выпавших из него.

У каждого устройства своя очередь для каждого контакта. Сообщение уходит по
разу на устройство: каждому устройству контакта, в его очередь, и копией
каждому своему другому устройству, в его очередь для этого контакта.
`Inner.sender` и `recipient` — ключи устройств; у основного они совпадают с
личностью, так что старые клиенты разницы не видят. Наша очередь для контакта
читает от его основного, от любого устройства из его списка (как от контакта)
и от наших устройств (как наше). Устройство представляется контакту через
`Devices`, никогда через `QueueOffer`, который сдвинул бы, куда он пишет всей
личности. Контакты ниже уровня `Understands` 3 слышат только основное.

### Несколько администраторов (ADR-042)

```
AdminList { group: [u8; 16], no: u64, signer: [u8; 32], admins: Vec<[u8; 32]>,
            resign: Option<Resign>, signature: [u8; 64] }
Resign { roster_no: u64, signature: [u8; 64] }
AdminGrant { queue: [u8; 16], token: [u8; 32] }

Body += GroupAdmins { group: [u8; 16], chain: Vec<AdminList> }  // перед составом: в группе, в приглашении, при переезде
      | GroupResign { group: [u8; 16], resign: Resign }         // основной -> группе, внутри Megolm
      | GroupAdminKeys { group: [u8; 16], roster_no: u64, grant: AdminGrant }  // только через Olm
```

В `admins` от 1 до 4 личностей: первым основной администратор, затем
остальные в порядке назначения, без повторов. `no` — состав, с которым пришёл
список; `signer` — администратор предыдущего списка. Список подписан по
`"termchat-admins-v1" || postcard(group, no, signer, admins, resign)`,
заявление основного — по `"termchat-resign-v1" || postcard(group, roster_no)`.
У группы без списков один администратор — создатель, `admin` состава.

Участник принимает состав N+1, только если его подписал администратор
действующего списка, а его списки, от старого к новому, каждый следуют за
предыдущим: основной назначает, снимает и упорядочивает администраторов или
передаёт роль (преемник первым, основного больше нет); другой администратор
только убирает себя; следующий принимает дела только с `Resign` основного за
состав N. Состав не от основного только добавляет участников после
существующих и не меняет название и таймер. Каждый действующий администратор
— участник. `Roster.admin` называет подписавшего состав. Переносит группу
только состав основного.

`GroupAdminKeys` несёт токен администратора очереди группы от основного к
основному устройству другого администратора и ждёт состава, который назовёт
его администратором; внутри сообщения группы и внутри `Copy` он отвергается.
Участникам, которые не контакты администратора, `GroupAdmins`, `GroupMove`,
`GroupLeave` и `GroupAdminKeys` идут через их читателя, по Olm с ключом,
взятым из него. После переезда основной убирает читателей исключённых через
`RemoveReaderAt` и удаляет старую очередь, когда каждый, кому сказали через
неё, написал в новую, или через сутки. Клиент пишет в группу, только когда
relay прислал `KeyCount` для его читателя, после всего, что ждало. Составам
от нескольких администраторов нужен уровень `Understands` 6 у всех устройств
участников.

## 10. Отпечаток

Схема как в Signal: у каждого ключа свой отпечаток, номер безопасности — оба отпечатка подряд.

- **Отпечаток ключа**, 30 цифр: `h = SHA-512("termchat-fp-v1" || ed25519)`. Первые 30 байт `h` делятся на 6 кусков по 5 байт. Каждый кусок читается как big-endian число и берётся по модулю 100000, получается группа из 5 цифр.
- **Номер безопасности** пары, 60 цифр: отпечатки обоих ключей в порядке сортировки ключей, 12 групп по 5 цифр. Одинаковый у обоих собеседников.

Почему не хеш от пары ключей: при MITM атакующий выбирает оба своих ключа и ищет совпадение номеров атакой «дней рождения» (~2^(n/2) попыток). С отдельными отпечатками ему нужен ключ с таким же отпечатком, как у конкретного человека: ~2^99 попыток.

## 11. Лимиты (значения по умолчанию, настраиваются в relay)

| Что | Значение |
|---|---|
| Размер WS-фрейма | 72 KiB |
| `body` конверта | 65536 + накладные расходы Olm, не больше 68 KiB |
| `Send` в одну очередь от всех | token bucket: 30 подряд, затем 1 в секунду (ADR-043) |
| Соединений с одного IP | 50 (CGNAT: много людей за одним IP) |
| Любых кадров на соединение | token bucket: 2000 залпом (вся очередь, подтверждаемая после переподключения), далее 20 в секунду; сверх того соединение закрывается |
| Новых очередей с одного IP | 20 в час (через onion: общий бюджет 200 в час, ADR-004) |
| One-time keys на очередь | очередь приглашения получает 50 (`Account::max_number_of_one_time_keys()`), очередь контакта 2; relay хранит не больше 100 новейших |
| `PublishKeys` на очередь | 30 в час |
| `ClaimKey` на соединение | 30 в час |
| `ClaimKey` к одной очереди от всех | 100 в сутки (сверх лимита выдаётся только fallback key) |
| Время на `Hello` | 10 секунд после подключения |
| Запись клиенту | 30 секунд: кто не читает, тот отключается |
| Очередь | 1000 конвертов и 10 MiB, TTL 14 дней; неиспользуемые очереди удаляются через 90 дней |
| `Report` на соединение | 10 в сутки |
| Переполненный канал к онлайн-клиенту | relay рвёт соединение, клиент переподключается и получает очередь (ADR-007) |

Счётчики живут только в памяти. Незнакомцы попадают только в очередь приглашения, поэтому доли незнакомца в очереди контакта больше нет (ADR-023, раздел 6).

Подключения через Tor приходят с общих IP выходных узлов, поэтому лимиты по IP их несправедливо задевают. Для них relay публикует onion-адрес: у onion-подключений лимитов по IP нет, работают лимиты по очереди и соединению и общий бюджет onion-порта. Свой proof-of-work не реализован: его даёт Tor для onion-сервисов (ADR-004).

## 12. Коды ошибок

`UnsupportedVersion`, `Malformed`, `TooLarge`, `RateLimited`, `NoKeys`, `UnknownQueue`, `QueueFull`, `Internal`.

`UnknownQueue` означает и неверный токен. Ошибка не рвёт соединение, кроме `Malformed`.

## 13. Keepalive и реконнект

- Ping от relay каждые 30 секунд. Нет pong за 60 секунд — соединение закрывается.
- Клиент переподключается с экспоненциальной задержкой и случайным разбросом: от 1 до 60 секунд.
- Неподтверждённые `Send` клиент повторяет после переподключения. Дубликаты отсеивает получатель по `seq`.

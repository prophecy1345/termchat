# Протокол termchat, версия 1

Статус: черновик (M0), ждёт одобрения. Пункты с пометкой **[открыто]** решаются до M1.

## 1. Слои

1. **Транспорт:** WebSocket поверх TLS (`wss://`). TLS терминирует reverse proxy, relay видит обычный WS. Каждое сообщение — один бинарный WS-фрейм. Текстовые фреймы — ошибка протокола, соединение закрывается.
2. **Фреймы:** перечисления `ClientFrame` и `ServerFrame`, кодируются `postcard`. Используются для регистрации, ключей, отправки и доставки.
3. **Конверт:** то, что relay пересылает от клиента к клиенту. Тело конверта — сообщение Olm.
4. **Внутреннее сообщение:** открытый текст внутри Olm, с padding.

Все числа — в кодировке postcard (varint). Ключи Ed25519 и Curve25519 — 32 байта, подписи Ed25519 — 64 байта.

## 2. Версия

Первый фрейм клиента — `Hello { version: u16 }`. Сейчас `version = 1`. Если relay не поддерживает версию, он отвечает `Error { code: UnsupportedVersion }` и закрывает соединение. Конверт тоже несёт `version`, чтобы клиенты разных версий могли понять друг друга или явно отказать.

## 3. Регистрация (challenge-response)

```
C -> R  Hello { version }
R -> C  Challenge { nonce: [u8; 32] }
C -> R  Auth { ed25519, curve25519, signature }
R -> C  AuthOk | Error { code }
```

`signature` — подпись Ed25519 над байтами:

```
"termchat-auth-v1" || relay_host || nonce || curve25519
```

- `relay_host` из URL relay (например `relay.example.org`) не даёт переиспользовать подпись на другом relay.
- `curve25519` в подписи связывает ключ обмена с ключом подписи.
- Nonce одноразовый и живёт не дольше 30 секунд.

До `AuthOk` relay принимает только `Hello` и `Auth`.

## 4. Ключи (prekeys)

```
C -> R  PublishKeys { one_time: Vec<SignedKey>, fallback: Option<SignedKey> }
C -> R  ClaimKey { target: ed25519 }
R -> C  ClaimedKey { target, curve25519, key: SignedKey } | Error { code: NoKeys }
R -> C  KeyCount { one_time_left: u32 }
```

`SignedKey { key: [u8; 32], signature: [u8; 64] }`. Подпись Ed25519 владельца над `"termchat-otk-v1" || key`. Отдельный id не нужен: vodozemac находит one-time key по публичной части. Клиент, получивший ключ, проверяет подпись ключом `target`, поэтому relay не может подсунуть свой ключ.

Relay выдаёт one-time key один раз и удаляет. Если они кончились, выдаёт fallback key. Параметры (сколько публиковать, когда пополнять) — в ADR-002.

## 5. Отправка и доставка

```
C -> R  Send { client_id: u64, envelope: Envelope }
R -> C  Accepted { client_id } | Error { client_id, code }
R -> C  Deliver { relay_id: u64, sender: ed25519, envelope: Envelope }
C -> R  Ack { relay_id }
```

- `Accepted` означает, что relay принял конверт. В клиенте это «доставлено на сервер». E2E-квитанций о прочтении нет.
- `sender` в `Deliver` ставит relay по аутентифицированному соединению. Клиент не доверяет этому полю: настоящий отправитель подтверждается расшифровкой и проверкой внутреннего сообщения (раздел 7).
- `Ack` разрешает relay удалить конверт (важно с M5, когда появляется очередь).

## 6. Конверт

```
Envelope {
    version: u16,
    recipient: [u8; 32],      // ed25519 получателя
    olm_type: u8,             // 0 = pre-key, 1 = normal
    body: Vec<u8>,            // шифртекст Olm
}
```

Поля отправителя нет: так в будущем можно добавить sealed sender, не меняя формат.

## 7. Внутреннее сообщение

Открытый текст до шифрования Olm:

```
Inner {
    sender: [u8; 32],         // ed25519 отправителя
    recipient: [u8; 32],      // ed25519 получателя
    body: Body,
}

Body =
    ContactRequest { note: String }      // первое сообщение незнакомцу
  | ContactAccept
  | Text { id: [u8; 16], sent_at: u64, expires_in: Option<u32>, text: String }
```

Проверки при получении:
1. `recipient` совпадает со своим ключом.
2. `sender` совпадает с ключом, к которому привязана сессия Olm. Для pre-key сообщения: Curve25519 из сообщения совпадает с ключом, который `sender` подписал при регистрации; ключ получаем через `ClaimKey` или из приглашения.
3. Иначе сообщение отбрасывается.

Сообщения от ключей, которых нет в контактах, показываются только в «запросах». Классификацию делает клиент, relay не знает список контактов.

## 8. Padding

Сериализованный `Inner` дополняется до ближайшего бакета: `0x80`, затем нули (ISO/IEC 7816-4). Бакеты: **256, 1024, 4096, 16384 байт**. Больше 16384 — ошибка `TooLarge`. **[открыто]** Набор бакетов и лимит длины `text`; предложение: 4000 символов.

## 9. Строка-приглашение

```
termchat:<base64url(postcard(Invite))>

Invite { version: u16, relay_url: String, ed25519: [u8; 32], curve25519: [u8; 32] }
```

Fallback key в приглашение не кладётся: он ротируется и быстро устареет. One-time key берётся через `ClaimKey`, подпись защищает от подмены. **[открыто]** Нужен ли короткий вариант для ручного ввода.

## 10. Отпечаток

**[открыто]** Предложение: номер безопасности на пару контактов, одинаковый у обоих. `SHA-256(min(A, B) || max(A, B))`, где A и B — ключи Ed25519. Первые 30 байт превращаются в 12 групп по 5 цифр. Это хеш, а не протокол; окончательный вариант фиксируется в ADR.

## 11. Лимиты (значения по умолчанию, настраиваются в relay)

| Что | Значение |
|---|---|
| Размер WS-фрейма | 64 KiB |
| `body` конверта | 16384 + накладные расходы Olm, не больше 20 KiB |
| `Send` от одного ключа | 30 в минуту |
| Новых получателей от одного ключа | 20 в сутки |
| Соединений с одного IP | 10 |
| Новых регистраций с одного IP | 5 в час |
| One-time keys на ключ | не больше `Account::max_number_of_one_time_keys()` (значение проверить в M1) |
| `ClaimKey` от одного ключа | 30 в час |
| Очередь на получателя (M5) | 1000 конвертов, TTL 14 дней |

Счётчики живут только в памяти.

## 12. Коды ошибок

`UnsupportedVersion`, `Malformed`, `TooLarge`, `NotAuthenticated`, `BadSignature`, `ChallengeExpired`, `RateLimited`, `NoKeys`, `UnknownRecipient`, `QueueFull`, `Internal`.

Ошибка с конкретным `client_id` не рвёт соединение. `Malformed`, `BadSignature`, `NotAuthenticated` закрывают соединение.

## 13. Keepalive и реконнект

- Ping от relay каждые 30 секунд. Нет pong за 60 секунд — соединение закрывается.
- Клиент переподключается с экспоненциальной задержкой и случайным разбросом: от 1 до 60 секунд.
- Неподтверждённые `Send` клиент повторяет после повторной аутентификации. Дубликаты отсеивает получатель по `Text.id`.

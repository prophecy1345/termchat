# ADR-004: Tor

Status: accepted, implemented in M6. Date: 2026-10-15. Русская версия: [004-tor.ru.md](004-tor.ru.md).

## Context

The relay sees every client's IP (in memory, for rate limits). The provider sees
that the user talks to a relay. Tor hides both. It does not protect against a
global observer correlating traffic timing; that stays under "not protected".

Reaching the relay through a Tor exit is a bad fit: exits share IP addresses, so
per-IP limits hit all their users at once. Tor clients therefore use the relay's
**onion address**.

## Decision

### Relay: no Tor code, C tor next to it
- The operator installs the system `tor` and publishes an onion service pointing
  at a separate local port of the relay:

  ```
  HiddenServiceDir /var/lib/tor/termchat/
  HiddenServicePort 80 127.0.0.1:8081
  HiddenServicePoWDefensesEnabled 1
  ```

- C tor has years of scrutiny, and Tor's built-in DoS defence for onion services
  (proof-of-work, `HiddenServicePoWDefensesEnabled`) removes the need for a
  proof-of-work of our own.
- **Important (found while testing):** the proof-of-work module is not in every
  `tor` build; it needs `--enable-gpl`. Homebrew's build lacks it, and `tor` with
  that line will not start. The Debian/Ubuntu package and the Tor Project's
  builds have it. Without it the onion service works, minus this defence.
- The relay gets `--onion-listen 127.0.0.1:8081`. Every connection on that port
  comes from `127.0.0.1`, so for them:
  - per-IP limits do not apply;
  - instead there is a shared budget for all onion connections: at most 2000
    connections and 200 new registrations per hour (`Limits`);
  - per-key limits work as usual.
- `--host` can be given several times (`relay.example.org` and `xxxx.onion`): the
  client signs the address it came through.

### Client: Arti built in
- `arti-client` 0.47 with the `tokio`, `rustls` (no OpenSSL),
  `onion-service-client`, `compression` and `static-sqlite` features.
- WebSocket over an Arti stream: `tokio-tungstenite::client_async` with
  `ws://xxxx.onion/`. No TLS over onion: the onion address authenticates the
  server and encrypts the channel by itself.
- Arti's state (guards, directory cache) lives in `~/.termchat/arti`, mode
  `0700`. It is deleted together with the state file by a wipe or the duress
  password (ADR-003): it holds no secrets, but shows that Tor was used.
- **No leaks around Tor:** with Tor on, the client never connects directly, even
  if Tor fails to start. The status bar says "connecting via Tor…".
- Build: the client's `tor` cargo feature. On in official releases, off for a
  minimal build.

### Invites
- `Invite` gets an optional `onion_url`. An invite is accepted if at least one
  relay address matches, plain or onion, so users of one relay with and without
  Tor can add each other.
- The format had not shipped in any release yet, so the version stays 1. After
  the first release (M6) any format change bumps `version`.

### Settings
- On first run the client asks for the relay address and, if the relay has one,
  the onion address and "Use Tor? (y/n)".
- It can be switched in the settings. Turning Tor on forbids direct connections
  at once; turning it off warns that the relay will see the IP.

## Cost

- **Dependencies:** Arti is about 250 crates and adds 10–15 MB to the binary. All
  MIT/Apache, checked by `cargo deny`. Hence a separate cargo feature.
- **Latency:** the first connection takes 10–30 seconds (directory download),
  then 1–3 seconds per message.
- **Operator effort:** a relay with an onion address needs the system `tor`.
  Without it the relay works as before.

## Threat model changes
- Protected (optional): neither the relay nor the provider sees the user's IP
  when Tor is on.
- Still not protected: a global observer and timing correlation. The relay still
  sees keys and message times.

## Rejected
- **An onion service inside the relay through Arti (`onion-service-service`):**
  less proven than C tor; the system `tor` is simpler and more reliable for the
  operator.
- **The client through a system `tor` (SOCKS5):** an extra install for users;
  Arti is built into the binary.
- **A proof-of-work of our own for registration:** Tor already has one for onion
  services.

## Answers to the open questions
1. Tor is chosen on the first-run screen, with "y" suggested.
2. The `tor` feature is on in official releases (one binary).

## Outcome
- Client release binary: 20.7 MB, about 640 crates in the tree.
- New licences in the tree (all AGPL-compatible): CC0-1.0, Unlicense, MPL-2.0.
- `cargo deny` exceptions with reasons: RUSTSEC-2024-0436 (`paste`, a build-time
  proc-macro), RUSTSEC-2023-0071 (`rsa`, an attack on private-key operations,
  which a Tor client does not perform).
- Tested live: a relay behind the system `tor` 0.4.9, a client through Arti
  connected in 6 seconds, messages both ways with a client without Tor in about
  2 seconds, switching Tor in the settings.

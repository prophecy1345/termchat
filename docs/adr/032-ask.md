# ADR-032 — Script approvals with `termchat ask`

Status — **accepted by the maintainer**. [Русская версия](032-ask.ru.md).

## Context

A script or CI job can pause before a step such as a deployment and ask a person for approval in termchat. The script defines the step in advance. `ask` returns a decision as an exit status.

## Decision

### Command and reply

```sh
termchat ask alice "Deploy build 42 to staging?" --timeout 10m
```

The command uses the existing [daemon](029-daemon.md) for its `TERMCHAT_HOME` on Linux and macOS. The default timeout is 10 minutes. `ask` accepts positive whole seconds or whole minutes with the `m` suffix. The timeout includes time spent delivering the question.

The daemon resolves the contact once, requires an accepted and fingerprint-verified contact, and pins the public key of their primary device. It sends the question as an ordinary Olm-encrypted direct message with a fresh random code from the OS, encoded as 16 lowercase hexadecimal digits. The message includes both possible replies. For example, the contact sends `yes f4bc2801e9029d71` or `no f4bc2801e9029d71` from their primary device. The entire reply must match one of those forms exactly, with a single ASCII space. The contact can use the app's reply action or send a plain text message. Existing mobile clients can do either.

| Exit status | Meaning |
| --- | --- |
| `0` | The contact answered `yes`. |
| `1` | The contact answered `no`. |
| `2` | Invalid arguments or unsupported platform. |
| `3` | Contact not found or ambiguous. |
| `4` | No valid reply before the deadline. |
| `5` | Contact ineligible, request already pending for that contact, or permanent send failure. |
| `6` | Daemon unavailable, connection lost, or internal error. |

Only `0` authorizes the step. The CLI leaves stdout empty and sends diagnostics to stderr, omitting the question, code and reply. An unexpected daemon response is an internal error.

### Matching and lifetime

The daemon holds one pending request per pinned contact in memory. A second request to that contact returns a busy error and the first keeps waiting. The deadline uses a monotonic clock and starts when the daemon registers the request, before it queues the question. The first valid reply consumes the request and completes the command. The daemon clears a request on timeout, CLI disconnect, permanent send failure, or loss of contact eligibility. A daemon restart drops all pending requests. Every new request gets a fresh code. A queued question can still arrive after the request closes, and a reply to that question has no effect.

Only while the request is active, check newly received original direct text (`Body::Text` or `Body::Message`) for the exact reply. Carry the authenticated Olm sender and queue identity from receipt, before the engine maps linked-device senders to the primary contact for display. Both the sender key and the direct queue must match the pinned contact, and the contact must still qualify at the time of the decision. Use the original text bytes and complete the request only after successful persistence, before the deadline. Linked devices, copies, group messages, invitation messages, edits, reactions and history entries are ineligible. A relay acknowledgement only describes transport progress.

The engine observes receipt independently of `recv`. The question and reply still behave like ordinary messages in history, notifications and `recv`. The design uses the existing message format, relay and encryption.

## Threat model and limits

Another contact cannot approve a request, even with its code. The code binds an answer to one request and the pinned key authenticates the sender. Anyone able to send from the verified primary device can approve a pending request. This includes someone with an unlocked stolen phone or its private keys. The script can proceed only with the action it already defined. The remote reply supplies neither a shell command nor arguments for that action. Someone who controls the script or daemon's local account can bypass the local guard.

The relay can delay or drop traffic and sees the usual message metadata. Users should check the service identity in the chat before approving. Questions and replies may appear in chat history and notifications. The question passed as an argument can also appear in shell history and CI logs. Keep secrets out of the question.

## Alternatives considered

- **Waiting through `recv`.** It consumes unread state and omits the raw sender and queue needed to authenticate the decision.
- **A dedicated message type.** Explicit approval controls would require client and protocol changes. Ordinary text lets existing clients answer.

## Acceptance criteria

Use a local relay to exercise `yes`, `no`, timeout and daemon loss. Check the deadline boundary, concurrent requests to one contact, `recv --follow` running alongside `ask`, and cancellation after contact eligibility changes. The security audit must trace the authenticated sender and queue through to the exit status and check replies from another contact that knows the code, linked devices, copies, groups and invitations. Wrong text, edits, duplicates, late replies and replies to an earlier request, including after a daemon restart, must never authorize the script. Confirm that only a valid `yes` returns `0` and no failure is reported as `no`.

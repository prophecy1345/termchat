# ADR-029: режим службы для скриптов

Статус: **принято** (владелец, 2026-11-18). English version: [029-daemon.md](029-daemon.md). Пересматривает решение 1 из [ADR-024](024-scriptable-mode.ru.md).

## Контекст

В скриптовом режиме (ADR-024) каждая команда расшифровывает состояние, подключается к relay, делает дело и выходит. Для редкого уведомления это правильно, для большего — медленно:

- **Бот, который отвечает.** «status» с телефона и ответ за секунду. Через Tor каждый `send` — новое подключение, 10–30 секунд.
- **Частые уведомления** из CI, cron и мониторинга: каждому скрипту нужен файл с паролем, и каждый подключается сам.
- **Несколько скриптов на одной личности:** второй получает «already open» и падает (ADR-024, раздел 5).

Владелец попросил режим службы (2026-11-18).

## Решение

### 1. `termchat daemon`

```
termchat daemon [--password-file PATH | --password-stdin]
```

- Разблокирует личность один раз (те же источники пароля и то же поведение пароля под принуждением, что в ADR-024, раздел 2), держит блокировку состояния, не рвёт связь с relay и запускает таймеры движка, как TUI.
- Слушает **Unix-сокет в папке состояния**: `$TERMCHAT_HOME/daemon.sock`. Папка уже `0700`, сокет создаётся `0600`. Сокет, оставшийся от упавшей службы, удаляется при запуске, но только после проверки, что на нём никто не отвечает.
- **Проверка собеседника:** идентификатор пользователя на каждом подключении (`peer_cred`, от ядра) должен совпадать с пользователем службы; иначе подключение молча закрывается.
- Ни TCP, ни HTTP, ничего в сети (открытый порт ADR-024 отклонил, так и остаётся).
- Останавливается по SIGTERM или SIGINT: сохраняет состояние, удаляет сокет, выходит с кодом 0.
- Только Unix (Linux, macOS). На Windows `termchat daemon` говорит, что не поддерживается.

### 2. Команды пользуются ею сами

`send`, `send-file`, `recv`, `contacts`, `invite` и `add` сначала ищут запущенную службу для того же `TERMCHAT_HOME`. Если она отвечает, работают через неё и **пароль не нужен**. Если нет, работают как сейчас. `init` через службу не работает никогда.

Скрипт не меняется: тот же `termchat send owner "backup failed"` при запущенной службе выполняется примерно за миллисекунду.

### 3. Протокол сокета

Один JSON-объект на строку в каждую сторону, в той же форме, что `recv --json` (ADR-024, раздел 4):

- запрос: `{"cmd": "send", "to": "...", "text": "..."}`, `{"cmd": "send_file", "to": "...", "name": "...", "data": "<base64>"}`, `{"cmd": "recv", "from": null, "wait": 30, "follow": false}`, `{"cmd": "contacts"}`, `{"cmd": "invite"}`, `{"cmd": "add", "invite": "..."}`;
- ответ: `{"ok": true, ...}` или `{"ok": false, "code": 3, "error": "..."}`, с кодами выхода из ADR-024, раздел 3; `recv` шлёт строку на каждое сообщение, затем `{"ok": true}`, если не следит дальше.

Файл для `send-file` читает команда, а не служба: служба не открывает переданные ей пути. Лимиты — из ADR-017 (1 МБ на документ), строка запроса больше 2 МБ отклоняется.

Текст от контактов служба очищает (`clean_text`) перед отправкой, как в ADR-024.

### 4. Несколько читателей

- `recv` без `--follow` забирает непрочитанные и отмечает их прочитанными, как сейчас.
- Каждый `recv --follow`, подключённый в этот момент, получает каждое новое сообщение; оно отмечается прочитанным, как только его получил хоть один.
- Не больше 16 подключений одновременно; лишние закрываются.

## Модель угроз

- **Пароль и ключи остаются в памяти**, пока служба работает. Кто получил root или пользователя службы, читает и пишет от имени этой личности. Так было и с файлом пароля рядом с состоянием (ADR-024), и с открытым TUI. Служба — для серверной личности, никогда для основной; документация говорит это прямо.
- **Сокет — дверь для любого процесса этого пользователя.** С файлом пароля было то же: любой процесс пользователя мог его прочитать. Проверка собеседника не пускает других пользователей; для песочницы нужен отдельный пользователь.
- **Для relay ничего нового:** те же очереди; одно долгое подключение вместо многих коротких, и время отправки больше не выдаёт себя свежим подключением перед ней.
- **Ни рассылок, ни принятия запросов** (правило 15, ADR-024): служба шлёт одному контакту за запрос, команды принять контакт у неё нет.

## Не новый криптографический протокол (правило 1)

Тот же движок, сессии и очереди. Меняется только то, как команды доходят до движка. Новых зависимостей нет: `UnixListener` и `peer_cred` из tokio, его возможность `signal` для SIGTERM, и `serde_json` и `base64`, которые клиент уже использует.

## Отклонено

- **TCP-порт на localhost:** подключиться может любой локальный пользователь; Unix-сокет проверяет пользователя собеседника.
- **Сокет в `/run` или `/tmp`:** общие папки; папка состояния и так закрыта.
- **Служба читает файлы по пути:** риск «обманутого посредника»; команда читает их от своего пользователя.
- **Отдельный бинарник `termchat-daemon`:** ещё один артефакт; подкоманды достаточно.

## Что меняется в коде

- `client`: `daemon` (слушатель, проверка собеседника, цикл запросов), а в `send`/`recv`/… — сначала попытка через сокет.
- Документация: раздел «Служба» в руководстве по скриптам (EN/RU) с юнитом systemd, строка в модели угроз, ссылка из ADR-024 на этот ADR.
- `core`, `proto`, `relay` и протокол `engine` не меняются.

## Заметки о реализации (2026-11-18)

1. Оставшийся сокет удаляется, когда служба уже держит блокировку состояния: блокировка и так доказывает, что другой службы для этой папки нет, и это надёжнее проверки сокета.
2. Запросы несут ещё `timeout` (сколько секунд ждать relay, как `--timeout`), а `recv` — `files`: отдавать ли документы. Отданный документ уходит из службы; команда проверяет, что папка `--save-dir` существует, прежде чем просить.
3. Читатель, не сохранивший документ, всё равно отмечает его прочитанным, как всегда делал `recv` без `--save-dir`.

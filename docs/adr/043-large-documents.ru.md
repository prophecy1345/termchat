# ADR-043: документы до 25 МиБ, отправка только по запросу получателя

Статус: **принято** (владелец, 2026-11-24). English version: [043-large-documents.md](043-large-documents.md). Расширяет [ADR-017](017-documents.ru.md) (документы как непрозрачные байты), использует проверку уровня из [ADR-041](041-delivery-and-read-receipts.ru.md). PLAN.md P11.

## Контекст

ADR-017 ограничивает документ 1 МиБ (`MAX_FILE_BYTES`). Обычный скан, фото или презентация в него не влезают, и люди уходят из termchat в менее приватный канал.

ADR-017 отверг простое повышение лимита внутри Olm. Мешают три вещи:

- **Темп.** Relay принимает в одну очередь 30 `Send` разом, дальше 1 раз в 2 с (`sends_per_queue`). Кусок — 16 000 байт в корзине 16 КиБ. 25 МиБ — около 1 640 кусков, почти час.
- **Квота очереди.** Очередь вмещает 10 МиБ (`queue_bytes`). Файл в 25 МиБ, отправленный человеку не в сети, забьёт очередь и задержит его текст.
- **Ненужные байты.** Сейчас отправитель толкает файл, и получатель получает каждый байт, нужен он ему или нет. При 1 МиБ это терпимо. При 25 МиБ это трафик и батарея получателя и простой способ ему досадить.

Правило 1 исключает путь Matrix (зашифрованный блоб на relay, ключ по Olm): в vodozemac нет шифрования вложений, а комбинировать примитивы самим нельзя. Поэтому байты остаются внутри обычных Olm-сообщений, и ADR меняет то, как они отправляются, а не то, как шифруются.

## Решение

### 1. Два способа отправки

- **До 1 МиБ: толкаем, как сейчас** (ADR-017 без изменений).
- **Больше 1 МиБ и до 25 МиБ: предложение, потом отправка по запросу.** Отправитель шлёт короткое предложение. Байты идут только после того, как получатель нажмёт «Скачать».

### 2. Новые варианты `Body`

Добавляются в конец `Body`, кодирование существующих вариантов не меняется:

```rust
Body::FileOffer {
    id: u32,                  // случайный, один на передачу
    name: String,             // правила как в ADR-017
    size: u32,                // 1 ..= MAX_LARGE_FILE_BYTES
    expires_in: Option<u32>,  // таймер исчезновения чата
}
Body::FileWant  { id: u32 }            // получатель: присылай
Body::FileAck   { id: u32, next: u16 } // получатель: все куски до `next` дошли
Body::FileStop  { id: u32 }            // любая сторона: отмена, забыть передачу
Body::FilePart  { id: u32, index: u16, data: Vec<u8> }
```

Проверяется в `proto`, значит, проходит fuzz:

- `MAX_LARGE_FILE_BYTES = 26_214_400` (25 МиБ).
- `LARGE_CHUNK = 64_000`, значит, не больше 410 кусков. `index < ceil(size / LARGE_CHUNK)`.
- `data.len()` ровно `LARGE_CHUNK`, кроме последнего куска: в нём ровно остаток.
- `FilePart` принимается только для `id`, который получатель запросил через `FileWant`, и только по порядку (`index == next`). Остальное отбрасывается, а пропуск отменяет передачу с системной строкой, как в ADR-017, раздел 3.

### 3. Корзина побольше для кусков

- В `BUCKETS` появляется четвёртый размер, **65 536**. Его использует только `FilePart`. Текст и всё остальное остаются в трёх прежних размерах.
- `MAX_FRAME_BYTES` растёт с 64 КиБ до **72 КиБ**, чтобы вместить конверт 64 КиБ с заголовком. Relay берёт новый лимит из `proto`.

### 4. Темп и управление потоком

- У отправителя не больше **64 неподтверждённых кусков (4 МиБ)**. Получатель шлёт `FileAck` каждые 16 кусков. Передача никогда не занимает больше 4 МиБ из 10 МиБ очереди получателя, и текст всегда влезает.
- **Меняется темп relay**: `sends_per_queue` с 1 раза в 2 с до **1 раза в секунду** (всплеск остаётся 30). Очередь от заваливания защищает квота, а не темп, и квота не меняется.
- Отправитель шлёт один кусок раз в 1,5 с и оставляет место для текста, как в ADR-017.
- 25 МиБ идут около **10 минут**. 4 МиБ — около полутора минут. Прогресс виден обеим сторонам.
- Устройствам нужно выходить в сеть, но не одновременно: куски ждут в очереди получателя, подтверждения — в очереди отправителя. Прерванная передача продолжается после перезапуска на любой стороне.

### 5. Кто может отправлять и получать

- Только принятые контакты, как в ADR-017, раздел 5. Предложение от незнакомца, от ещё не принятого запроса или от заблокированного контакта отбрасывается.
- Предложения уходят только контактам с **`Understands` уровня 7**. Для более старого контакта приложение пишет «их приложение принимает документы до 1 МиБ» и отправляет толчком то, что влезает.
- **Группы остаются на 1 МиБ** в этом ADR. У группы одна общая очередь, и куски для одного участника дойдут до всех 32. Большим файлам в группах нужен свой ADR.
- **Связанные устройства** (ADR-028) не получают копию отправленного большого файла, только строку в истории.

### 6. Отправитель хранит копию, пока её не заберут

- При «Отправить» приложение читает файл один раз (IO делает вызывающий код, правило 11) и кладёт зашифрованную копию в свой спул (раздел 7). Дальнейшие изменения оригинала не важны.
- Предложение живёт **7 дней**. После этого или после `FileStop` отправитель удаляет копию, и оба чата показывают «не забрали».
- Не больше **4 ждущих предложений** на отправителя и не больше **100 МиБ** в спуле всего.

### 7. Спул на диске: запечатанные записи рядом с файлом состояния

Файл в 25 МиБ не может жить в JSON-файле состояния: этот файл переписывается целиком при каждом изменении.

- У каждой передачи свой файл спула рядом с файлом состояния, со случайным именем.
- Каждый кусок хранится одной записью: `seal(file_key, id ‖ index ‖ data)`, та же `core::store::seal` (XChaCha20-Poly1305 со свежим случайным nonce), которая уже защищает файл состояния. Ни нового примитива, ни нового ключа.
- При сборке каждая запись открывается и проверяется: тот же `id`, `index` по порядку, ни одна запись не пропущена и не повторена. Только после этого файл можно сохранить.
- Лимиты у получателя: одна входящая большая передача на контакт, всего не больше **64 МиБ** несохранённых файлов (было 8 МиБ). Сверх лимита приложение не шлёт `FileWant` и объясняет почему.
- **WIPE, пароль под принуждением и удаление чата удаляют и файлы спула.** Таймер исчезновения действует на них, как на всё остальное.
- Движок остаётся без IO: он отдаёт вызывающему коду запись для записи или список записей для чтения.

### 8. Сохранение

Как в ADR-017, раздел 7: только явным действием, `create_new`, права `0600`, никогда не исполняемый, на Android через SAF. Файл пишется в цель из спула запись за записью, без всех 25 МиБ в памяти.

### 9. Уровень протокола

`UNDERSTANDS` становится 7.

## Последствия и честные пределы

- **Метаданные.** Relay видит корзину 64 КиБ и знает, что между двумя очередями идёт большой файл. Он может оценить размер с точностью около 64 КБ и видит, когда получатель его запросил. Это будет в threat-model.md, README и на сайте.
- **Скорость.** 10 минут на 25 МиБ — медленно по сравнению с Signal или Telegram. Это цена отсутствия файлового хранилища на relay.
- **Relay.** Старые relay отклоняют кадры в 72 КиБ. Тогда приложение отменяет передачу с «этот relay не принимает большие документы». Наш relay обновляется вместе с релизом (ADR-010).
- **Диск.** Спул получателя может держать до 64 МиБ в зашифрованном виде, пока файлы не сохранены или не удалены.
- **Сохранённый файл живёт вне termchat**, как в ADR-017.

## Отклонено

- **Зашифрованный блоб на relay** (как в Matrix, `age`): нужно шифрование вложений, которого нет в vodozemac (правило 1), хранилище блобов и API на relay, исключение из правила 14. Это по-прежнему путь для файлов больше 25 МиБ, в своём ADR.
- **Толкать большие файлы, как сейчас:** забивает очередь получателя и тратит его трафик на то, что ему может быть не нужно.
- **Держать куски в JSON-файле состояния:** файл переписывался бы целиком, до 25 МиБ, после каждого куска.
- **Большие файлы в группах:** одна общая очередь, нужен отдельный дизайн.

## Зависимости

Новых нет.

## Заметки о реализации (2026-11-24)

Где код расходится с текстом выше:

- **Чтение и запись спула — в `engine`**, который и так пишет файл состояния. `core` и `proto` остаются без IO (правило 11). Записи запечатывает `core::store::seal_record`: ключ данных и AEAD файла состояния, номер передачи и части — как связанные данные. Заголовок файла состояния в запись не входит, поэтому после смены пароля спул читается.
- **При сохранении файл собирается в памяти**, не больше 25 МиБ, из проверенных записей. Android получает байты через FFI, как и маленькие файлы.
- **Предложения и части идут только на основное устройство контакта**, а наши связанные устройства не получают ничего, даже строки в истории: `FileOffer` никогда не кладётся в `Copy`.
- **`termchat send-file` остаётся на 1 МиБ**: разовая команда не может ждать, пока контакт запросит файл. `termchat recv` предложения не показывает.
- Папка спула — `<файл состояния>.spool` рядом с файлом состояния. Файлы, которые больше не нужны ни одному сообщению, затираются на следующем такте, так что очистка или удаление чата их тоже освобождает. WIPE затирает папку.

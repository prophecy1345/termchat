# ADR-017: документы как непрозрачные байты внутри Olm-сообщений

Статус: **принято** (владелец, 2026-11-01). English version: [017-documents.md](017-documents.md).

## Контекст

termchat был только текстовым (правило 9). Людям иногда нужно передать документ: PDF, конфиг, публичный ключ, черновик договора. Сейчас для этого они уходят из termchat в канал, который обычно менее приватен.

Владелец решил (2026-11-01) разрешить **документы как непрозрачные байты**. termchat их не рендерит, не показывает превью и не открывает, картинок в чате нет.

Правило 1 запрещает самописную криптографию. В vodozemac 0.11 нет шифрования вложений: в Matrix ими занимается matrix-sdk-crypto (AES-CTR + SHA-256, ключ передаётся через Olm/Megolm).

## Решение

### 1. Транспорт: чанки в обычных Olm-сообщениях
Файл режется на куски. Каждый кусок — обычное сообщение `Inner` с новым вариантом тела. Его шифрует существующая Olm-сессия и дополняет до бакета 16384 байт. Нового примитива нет, новой зависимости нет, relay не меняется.

```rust
Body::File {
    id: u32,              // случайный, один на передачу
    name: String,
    size: u32,            // размер всего файла в байтах
    index: u16,           // номер куска с 0
    expires_in: Option<u32>,
    data: Vec<u8>,
}
```

Вариант добавляется в конец `Body` (postcard-индекс 5), поэтому кодировка старых вариантов не меняется. Имя и размер идут в каждом куске, отдельное сообщение «начало» не нужно.

### 2. Лимиты (проверяются в `proto`, поэтому попадают в fuzz)
- `MAX_FILE_BYTES = 1_048_576` (1 МиБ), `FILE_CHUNK = 16_000`. Кусков не больше 66.
- `0 < size <= MAX_FILE_BYTES`, `index < ceil(size / FILE_CHUNK)`.
- `data.len()` равно `FILE_CHUNK`. Последний кусок короче: в нём ровно остаток.
- `name`: от 1 до 255 байт, без управляющих и bidi-символов, без `/`, `\` и NUL, не `.` и не `..`.

### 3. Целостность и порядок
- Каждый кусок аутентифицирует Olm.
- Пропуски и так видно по `seq`.
- Получатель принимает куски только по порядку (`index == next`). Передача отменяется с системной строкой в чате, если:
  - кусок пропущен;
  - у того же `id` другой `size` или `name`;
  - посреди передачи пришёл новый `id`.
- Хеш не нужен: куски аутентифицированы, порядок проверяется.

### 4. Темп отправки
Relay разрешает 30 `Send` подряд, потом 1 в 2 с. Отказ relay случился бы после шифрования и оставил бы дыру в `seq`. Поэтому клиент сам держит темп:
- первые 10 кусков уходят сразу, дальше по одному в 3 с;
- остаток лимита остаётся тексту;
- 200 КБ уходят примерно за 10 с, 1 МиБ — примерно за 3 мин;
- прогресс виден в чате;
- незаконченная передача лежит в state-файле и продолжается после перезапуска.

### 5. Кто может отправлять
- Только принятые контакты.
- Куски, которые пришли, пока висит запрос контакта, и куски от незнакомцев отбрасываются. У незнакомца и так квота очереди 256 КиБ.
- Заблокированным и ушедшим отправлять нельзя.

### 6. Хранение у получателя
- Собранный файл лежит в зашифрованном state-файле, пока пользователь его не сохранит или не удалит.
- После этого в истории остаётся только строка `file name (size)`.
- Одна входящая передача на контакт за раз.
- Несохранённых файлов в сумме не больше 8 МиБ. Файл сверх лимита отбрасывается с системной строкой.
- Таймер исчезающих сообщений чата действует и на файлы.
- Удаление чата, WIPE и duress-пароль стирают файлы вместе со всем остальным.

### 7. Сохранение
- Файл сохраняется только явным действием пользователя.
- В терминале — в каталог, который выбирает пользователь (по умолчанию `~/Downloads`):
  - имя проходит через `clean()`;
  - файл создаётся через `create_new`, права `0600`, без бита исполнения;
  - существующий файл не перезаписывается, к имени добавляется ` (1)`, ` (2)` и так далее.
- На Android — через системный диалог «Сохранить как» (SAF). Разрешение на хранилище не нужно.
- termchat никогда не открывает файл и не угадывает его тип.
- Диалог сохранения предупреждает: «файлы от контактов могут быть вредоносными; termchat их не открывает».

## Последствия и честные ограничения
- **Метаданные.** Relay видит серию конвертов по 16 КБ от одного ключа к другому. По ней он оценивает размер файла с точностью около 16 КБ. Это нужно написать в threat-model.md, README и на сайте.
- **Сохранённый файл живёт вне termchat.** WIPE и duress-пароль его не стирают.
- **Старые клиенты** (до 0.4.0) не разбирают новый вариант и показывают «a message could not be decrypted» на каждый кусок. Нужна версия 0.4.0 у обеих сторон.
- **Правило 9 меняется на:** «Текст и документы как непрозрачные байты (ADR-017). Без рендеринга, превью, автооткрытия, картинок в чате и разметки сообщений».

## Отклонено
- **Шифрованный blob на relay, ключ через Olm** (как в Matrix или через `age`):
  - быстро и подходит для больших файлов;
  - но нужен новый крипто-формат и новая зависимость, хранилище и API на relay, исключение из правила 14;
  - можно вернуться к этому отдельным ADR, если 1 МиБ окажется мало.
- **Лимит больше внутри Olm.** Из-за квоты очереди получателя (10 МиБ) и лимита отправки 4 МиБ шли бы около 10 минут и занимали бы половину очереди.
- **Показ картинок.** Декодеры — классическая поверхность атаки, и терминалы показывают картинки по-разному.

## Зависимости
Новых нет. `base64` уже есть в `engine`, им несохранённые байты хранятся в JSON-состоянии.

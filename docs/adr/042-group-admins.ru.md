# ADR-042: несколько администраторов группы, передача и снятие роли

Статус: **принято** (владелец, 2026-11-23). English version: [042-group-admins.md](042-group-admins.md). Меняет [ADR-027](027-small-private-groups.ru.md), раздел 4 («передачу роли администратора откладываем»), и опирается на [ADR-028](028-second-device.ru.md) (устройства в группах) и [ADR-030](030-keys-by-someones-word.ru.md) (ключи со слов другого).

## Контекст

У группы ровно один администратор — создатель. Только он добавляет и исключает участников, ставит таймер исчезновения, держит токен администратора очереди на relay и подписывает состав своим ключом личности. Если он ушёл или потерял устройство, группа остаётся читаемой, но измениться уже не может.

PLAN.md P10 просил передачу роли. Владелец расширил задачу (2026-11-23):

1. **Добавить администратора** к существующему: из участника группы.
2. После этого **первого можно оставить или снять**, но снять его может только он сам. Передача роли — частный случай: назначить нового и уйти с роли.

Функция рискованная: она меняет, чьей подписи верят участники, и даёт токен очереди большему числу людей. Поэтому ниже отдельный раздел аудита.

## Решение

### 1. Основной администратор и помощники

- В составе появляется **упорядоченный** список **`admins`**: от 1 до **4** ключей личности, каждый из списка участников. **Первый в списке — основной администратор** (сначала это создатель). Остальные — **помощники**, в порядке назначения. Поле `admin` остаётся и значит «кто подписал этот состав». Подписавший должен быть в `admins`.
- **Цепочка доверия.** Участник принимает состав N+1, только если тот подписан администратором из **последнего принятого им** состава N и если подписавший имел право на каждое изменение между N и N+1 (таблица ниже). Первый состав приходит в приглашении, как сейчас: его подписывает приглашающий, и он должен быть в `admins`.
- В группе **всегда есть основной администратор**. Состав с пустым `admins` неверен.

**Кто что может.** Участник проверяет это сам, сравнивая N и N+1, а не верит подписавшему:

| Изменение между N и N+1 | Основной | Помощник |
|---|---|---|
| Пригласить своего контакта | да | да |
| Исключить обычного участника (в том числе вышедшего) | да | нет |
| Исключить администратора из группы | помощника — да | нет |
| Назначить помощника | да | нет |
| Снять помощника | да | только себя |
| Снять или исключить основного | только сам себя | нет (кроме раздела 4) |
| Название группы, таймер исчезновения | да | нет |
| Порядок `admins` | только при передаче (раздел 4) | нет |

Пока группой не начали пользоваться несколько администраторов, всё остаётся как в ADR-027: один основной, и он же создатель.

### 2. Кого можно назначить

- Назначает **только основной**, и только **участника группы**, у всех устройств которого уровень `Understands` не ниже 6 (раздел 7).
- Помощник может только **приглашать своих контактов**, как и создатель (ADR-027, раздел 4). Исключать он не может никого, кроме себя из `admins`. Участника, который вышел (`GroupLeave`), из состава убирает основной.
- Участники, которые не контакты помощника, верят ему в том же, в чём верили создателю: кто есть в группе. Те же проверки ADR-030 (ключ участника, известного нам как контакт, должен совпасть с ключом контакта; список устройств подписан самим участником) действуют для состава от любого администратора.

### 3. Права на очереди relay

Протокол relay **не меняется**. Токен администратора очереди группы (`AddReader`, `RemoveReader`) основной передаёт помощнику через Olm, один на один, новым видом сообщения **`GroupAdminKeys { group, roster_no, queue, token }`** внутри шифрования. Его получает только **основное устройство** помощника (ADR-028, раздел 7). Получатель принимает его, только если:

- он уже принял состав номер `roster_no` или новее, где он в `admins`;
- сообщение пришло по Olm от устройства, которое в списке устройств (ADR-028) администратора из этого состава;
- `queue` — текущая очередь группы.

Иначе сообщение отбрасывается молча. Токен хранится, как сейчас токен создателя: только в зашифрованном состоянии, `Zeroize`, без `Debug` со значением, не попадает в логи и ошибки (правило 6).

### 4. Уход основного: передача и выход

Основного не может снять никто, кроме него самого. Способов два:

- **Передача роли** («Hand over admin»): основной подписывает состав, где назначенный им участник стоит первым в `admins`, а он сам либо убран из `admins` (остаётся участником), либо исключён (уходит из группы). Если преемник не был помощником, это одновременно и назначение. Затем основной переносит группу (раздел 5) и передаёт токен новой очереди всем оставшимся администраторам.
- **Выход без указания преемника** (основной вышел из группы через `GroupLeave`): основным становится **следующий в `admins`**, то есть тот, кто был назначен раньше остальных. Если помощников нет, группа, как сейчас, остаётся без администратора и не меняется.

Во втором случае состав подписывает уже не основной, а его преемник. Чтобы помощник не мог объявить уход основного сам, выход основного несёт **подписанное заявление**: `GroupResign { group, roster_no }`, подписанное ключом личности основного с отдельным контекстом подписи (как подпись состава). Преемник вкладывает это заявление в свой состав N+1. Участник принимает состав, где основного больше нет, только если:

- его подписал сам основной из N, **или**
- в нём лежит `GroupResign` основного из N с `roster_no == N` и верной подписью, а подписал состав следующий по порядку в `admins`.

Заявление привязано к группе и номеру состава, поэтому его нельзя применить повторно или в другой группе. Проверяется оно без очереди: участник, который был офлайн, проверяет его по самому составу.

**Если основной потерял устройство** и не успел передать роль, снять его не может никто. Помощники могут только приглашать новых. Исключить никого нельзя, вышедшие остаются в составе, а название, таймер и назначения остаются как есть. Это цена защиты основного, и в приложении это так и сказано.

### 5. Снятие помощника и переезд

Снятый помощник остаётся участником, но **знает токен**. Поэтому после снятия или исключения любого администратора группа **переезжает в новую очередь**, как после исключения участника (ADR-027, раздел 4). Переезд делает подписавший новый состав. Новая очередь создаётся на его домашнем relay с новым токеном. Токен рассылается только оставшимся администраторам через `GroupAdminKeys`, а старая очередь удаляется: подписавший удаляет все её читатели (`RemoveReader`). Сессии Megolm меняются только если снятый ушёл из группы. Если он остаётся участником, он и дальше читает группу.

Если снятый успел вызвать `AddReader` или `RemoveReader` до переезда, это действует только в старой очереди. Новую очередь он не знает.

### 6. Двое меняют группу одновременно

Составы идут через очередь группы (`Body::GroupRoster` внутри Megolm). У одной очереди один порядок для всех читателей. Побеждает тот состав N+1, что **раньше записан в очередь**. Второй с тем же номером все отвергают по уже существующему правилу `roster.no <= current`. Проигравший видит чужой N+1 раньше своего, понимает, что его изменение не принято, и предлагает повторить его поверх: «изменение не применено: группу одновременно менял X; повторить?». Читателя, которого он добавил на relay, но не вписал в принятый состав, он удаляет (`RemoveReader`).

### 7. Старые клиенты

- `Understands` переходит на **уровень 6**: несколько администраторов.
- Пока в `admins` один ключ и это создатель, состав уходит в прежнем формате. Для старых клиентов группы с одним администратором не меняются.
- Состав с `admins` — **новый вид сообщения**. Старый клиент его не поймёт и перестанет видеть изменения группы. Поэтому назначить помощника или передать роль можно, только если **все устройства всех участников** сообщили уровень 6. Иначе приложение называет, кто должен обновиться. В группу, где уже несколько администраторов или основной не создатель, можно пригласить только контакт с уровнем 6.
- **Без отката формата.** Приняв хоть один состав нового вида, клиент больше не принимает для этой группы состав старого вида.

### 8. В приложениях

Основной видит в меню участника **Make admin**, а в меню помощника — **Remove admin**. Помощник видит у себя **Step down**. Основной видит **Hand over admin**: выбор участника и вопрос «остаться в группе или выйти». В списке участников основной и помощники помечены по-разному. Системные строки в чате у всех: «X made Y an admin», «X removed Y as admin», «Y stepped down as admin», «X handed the group over to Y», «X left; Y is now the main admin». Каждое изменение прав видно всем: тайно назначить или снять администратора нельзя.

## Что видит relay, честно

- Назначение помощника relay не видит: токен ходит внутри шифрования, а с relay говорят с тем же токеном.
- Снятие администратора или передачу роли relay видит как **переезд группы** в новую очередь, такой же, как после исключения участника. Отличить одно от другого он не может.
- Если новая очередь на другом relay (домашнем relay подписавшего), оператор прежнего relay видит, что группа ушла. Оператор нового видит, что группа пришла, и её размер.

## Это не новый криптопротокол (правило 1)

Подписи состава и `GroupResign` — Ed25519 ключами личности через vodozemac, как подпись состава сейчас, каждая со своим контекстом подписи. Меняется только **чьей** подписи верить: правила таблицы раздела 1 вместо одного ключа создателя. Токен передаётся через Olm, как ключи Megolm и приглашения. Megolm и Olm используются, как в ADR-027.

## Аудит безопасности

Нарушитель в каждом пункте — один из тех, кого мы готовы встретить: злонамеренный помощник, снятый администратор, участник, relay. Для каждого: что он может сделать, что мешает и что остаётся.

### А1. Помощник пытается захватить группу

- **Снять основного или исключить его.** Таблица раздела 1: участник отвергает состав, где основного нет или он не первый, если его не подписал основной и в нём нет его `GroupResign`. Проверяет каждый клиент, а не подписавший.
- **Подделать уход основного.** `GroupResign` подписан ключом личности основного и привязан к группе и номеру состава. Помощник не может его создать, а старый нельзя применить заново.
- **Назначить сообщника или поменять порядок `admins`**, чтобы стать следующим. Назначает и меняет порядок только основной.
- **Сменить название или таймер** (например, выключить исчезновение). Только основной.
- **Исключить остальных участников.** Не может: исключает только основной. Помощник может только пригласить своих контактов, это видно всем строкой в чате, а основной может исключить и приглашённых, и самого помощника.

**Остаётся: отключение на уровне relay.** Помощник знает токен очереди и может вызвать `RemoveReader` для читателя основного или любого участника, не меняя состав. Тогда тот перестанет получать сообщения группы, а остальные этого не увидят. Криптография от этого не защищает: relay не знает, чей читатель чей (ADR-023), и не может проверять состав. Защита:

1. Каждый клиент **замечает потерю своего читателя**: relay отвечает на подписку ошибкой «нет такой очереди». Приложение пишет «вас отключили от группы на relay» и предлагает спросить основного. Это уже есть для потерянных очередей (`queue_lost`), нужна только понятная строка для групп.
2. Основной, отключённый так, остаётся основным для всех участников, создаёт новую очередь и переносит в неё группу: перенос делает подписавший новый состав, а подписать может только он.
3. Злоупотребление видно по последствиям, а назначать помощников основной должен только тем, кому доверяет. Это пишется в подсказке к **Make admin**.

Отвергнутая альтернатива — отдельные токены на relay с правами только у основного — раскрыла бы relay структуру группы (раздел «Отклонено»).

### А2. Помощник уводит группу в свою очередь без основного

Переезд — это сообщение администратора участникам с адресом новой очереди. Если помощник переносит группу без основного, основной пишет в старую очередь, которую никто больше не читает.

Защита: участник принимает переезд, только если вместе с ним пришёл **новый состав, подписанный тем же администратором**, где у каждого участника, включая основного, новый читатель (`RosterMember.reader`). Если в составе нет основного, его отвергают по А1. Если основной в составе, но его читателя на relay не создали, это А1, «отключение на уровне relay», и основной видит потерю своего читателя.

### А3. Снятый администратор

- **Старый токен.** Работает только для старой очереди. Группа переехала (раздел 5), старая очередь удалена.
- **Составы от его имени.** Он больше не в `admins` последнего принятого состава, и его составы отвергаются.
- **Приглашения со старым составом.** Он может отправить своему контакту приглашение со старым составом, где он ещё администратор, и адресом старой очереди. Приглашённый попадёт в мёртвую группу, где никто не пишет. Вреда остальным участникам нет. Предел: приглашённый не может знать, что состав устарел. Это остаётся, приложение покажет «в группе давно нет сообщений».
- **Гонка: снять себя и успеть что-то сделать.** Всё, что он подписал после принятого состава со снятием, отвергается по номеру.

### А4. Передача токена

- **Поддельный `GroupAdminKeys`** от не-администратора или от администратора до того, как состав назначил получателя: отбрасывается (раздел 3).
- **Токен уходит не на то устройство.** Только на основное устройство из подписанного самим помощником списка устройств (ADR-028). Привязанные устройства токен не получают и не просят.
- **Утечка устройства любого администратора** даёт токен текущей очереди. Было одно устройство, станет до четырёх. Предел 4 и право основного снять помощника (с переездом) ограничивают это.
- **Токен в логах, ошибках, отладке.** Тип токена без `Debug` со значением, `ZeroizeOnDrop`. Негативный тест проверяет, что `format!("{:?}")` его не раскрывает.

### А5. Откат и развилка составов

- **Старый состав повторно** (с прежним `admins`): отвергается по номеру.
- **Состав старого формата** после перехода на новый: отвергается (раздел 7, «без отката формата»). Это закрывает обход таблицы через старую проверку `sender == admin`.
- **Две ветки N+1:** порядок в очереди один для всех (раздел 6), и все принимают одну и ту же. Новый участник получает состав из приглашения, подписанный приглашающим. Если приглашающий на проигравшей ветке, приглашённый перейдёт на общую ветку со следующим составом, подписанным администратором из его состава, или останется в мёртвой ветке, как в А3.
- **Участник был офлайн дольше 14 дней** и пропустил составы: цепочку он восстановить не может. Он ждёт повторной рассылки состава (ADR-028, решение 4). Повторная рассылка должна нести **всю цепочку изменений `admins` с N**, иначе он отвергнет состав, подписанный неизвестным ему помощником. Шорткат «принять последний, если подписан основным из N» безопасен, только если основной не менялся. В остальных случаях нужна цепочка.

### А6. Подмена ключей участников (ADR-030)

Помощник, как и создатель, ручается за ключи участников. Злонамеренный помощник может вписать в состав ключ, выдав его за известного нам человека. Проверки ADR-030 действуют для состава от любого администратора: ключ участника, который у нас в контактах, должен совпадать с ключом контакта, а участников, которых мы не сверяли, приложение помечает «добавлен администратором X; вы не проверяли». Новое только одно: в пометке указан конкретный администратор, а не «администратор».

### А7. Relay

Relay может переставлять, задерживать и удалять записи в очереди, но не может их подделать. Переставить два состава N+1 он может только одинаково для всех читателей одной очереди: порядок одной очереди общий. Отдать разным читателям разный порядок он может, если очередь хранит записи для каждого читателя отдельно. Тогда разные участники примут разные ветки N+1. Защита: следующий состав N+2 от любого администратора приходит с цепочкой (А5), и участник на другой ветке увидит расхождение и покажет «состав группы расходится, спросите основного». Полностью от злонамеренного relay это не защищает, как и сейчас: он может и просто не доставлять сообщения.

### Что проверить тестами до релиза

Негативные тесты на каждое «нет» таблицы раздела 1. Подделанный, чужой и повторно использованный `GroupResign`. `GroupAdminKeys` от не-администратора, до состава, на привязанное устройство, для чужой очереди. Состав старого формата после нового. Гонка двух составов N+1. Цепочка после пропуска. Fuzz разбора нового состава, `GroupResign` и `GroupAdminKeys` (правило 4). Проверка, что токен не попадает в `Debug`. Перед выпуском — отдельное ревью этого кода.

## Отклонено

- **Все администраторы равны** (первый вариант этого ADR): любой мог бы снять создателя. Владелец выбрал защиту основного.
- **Несколько токенов администратора на relay** (свой у каждого, `RemoveReader` только у основного): relay узнал бы, сколько в группе администраторов, протокол relay усложнился бы, а переезд при снятии всё равно нужен, потому что снятый знает `send_id`.
- **Голосование администраторов** за изменения: много кода и состояний для групп до 32 человек.
- **Передача без переезда:** снятый сохранил бы токен и мог бы добавлять читателей на relay.
- **Снятие основного помощниками, если он долго молчит:** любой порог времени — способ захватить группу, пока основной в отпуске.

## Уточнение при реализации (2026-11-23, одобрено владельцем)

Формат состава (`Roster`) **не меняется**. Список администраторов — отдельный подписанный объект **`AdminList { group, no, signer, admins, resign, signature }`**: `no` — номер состава, с которым он пришёл, `signer` — администратор предыдущего списка, `resign` — `GroupResign` основного, если подписывает преемник. Новые виды сообщений:

- **`GroupAdmins { group, chain }`**: цепочка списков, от старого к новому, не больше 8. Идёт прямо перед составом в том же канале: в группе, в приглашении, при переезде. Отставший участник проверяет цепочку от своего последнего списка (А5), не получая старых составов целиком: состав на 32 участника весит около 5 КБ, цепочка из 8 списков — около 3 КБ.
- **`GroupResign { group, resign }`**: заявление основного, в группе, перед его `GroupLeave`.
- **`GroupAdminKeys { group, roster_no, grant }`**: токен, только по Olm. Proto отвергает его внутри группы и внутри `Copy` для своих устройств.

Список вступает в силу, только когда принят состав с тем же `no` от того же `signer`. Проиграв гонку составов (раздел 6), список отбрасывается вместе с составом. Поле `admin` состава — его подписавший, он должен быть в действующем списке.

Отсюда меняется раздел 7: вместо «нового вида состава» — `GroupAdmins` рядом со старым составом. Старый клиент отвергнет состав, подписанный не создателем, поэтому условие «все устройства на уровне 6» остаётся. Пункт «без отката формата» больше не нужен: формат один. Вместо него правило: пока у группы есть принятый `AdminList`, состав без подходящего списка от того же подписавшего проверяется по последнему принятому списку, а не по полю `admin` старого состава.

## Решения владельца (2026-11-23)

1. Создателя (основного) снять нельзя: он уходит только сам.
2. Не больше 4 администраторов.
3. Название и таймер меняет только основной, а после его ухода — тот, кто стал основным после него.
4. Отдельное внимание аудиту безопасности: функция рискованная.
5. Назначает помощников только основной.
6. Помощник может только приглашать, исключает только основной.

# ADR-020: повтор отправки, которую relay временно отклонил

Статус: **принято** (владелец, 2026-11-11). English version: [020-send-retry.md](020-send-retry.md).

## Контекст

`Client::encrypt` даёт каждому сообщению следующий `seq` (protocol.md, раздел 7)
и сдвигает храповик Olm ещё до того, как конверт уйдёт с устройства. Если relay
затем отклонит конверт, этот `seq` потрачен и никогда не придёт. До конца сессии
трекер получателя показывает «⚠ 1 message(s) missing so far».

Сейчас отклонённый `Send` заканчивается так:

- **Текст:** сообщение становится `Failed`. Повторная отправка шифрует новый
  конверт с новым `seq`, а старый номер остаётся пропавшим навсегда.
- **Кусок файла:** у любого куска, кроме последнего, `client_id` не привязан
  ни к одному сообщению. `set_status` ничего не находит, и отказ теряется без
  следа. Отправитель видит файл отправленным, а получатель получает
  «did not arrive whole», потому что куски принимаются только по порядку
  (`Data::take_chunk`).

Часть отказов временные: те же байты relay примет позже.

| Код | Значение | Временный |
|---|---|---|
| `RateLimited` | у отправителя кончился лимит `sends_per_key` или лимит новых получателей | да |
| `QueueFull` | переполнена очередь получателя или общая очередь relay | да |
| `Internal` | ошибка базы на relay | да |
| `UnknownRecipient`, `Banned` | получателя больше нет или он забанен | нет |
| `TooLarge`, `Malformed` | ошибка в самом конверте | нет |

Проще всего исчерпать лимит отправки файлом: по ADR-017 сначала уходят 10 кусков
подряд, затем по одному раз в 3 с, и параллельно идут обычные сообщения.

## Решение

### 1. Временный отказ: повтор того же конверта
Если relay отвечает `Error { client_id: Some(id), code }` с временным кодом,
relay link (`crates/engine/src/relay.rs`) оставляет этот `Send` в `pending` и
позже отправляет **тот же фрейм** снова. Engine об этом не узнаёт, поэтому
сообщение остаётся в статусе `Sending`.

- Пауза 2 с, затем удваивается до 60 с, с тем же разбросом (jitter), что и при
  переподключении.
- Число попыток не ограничено, пока жив link. Relay хранит очередь 14 дней.
  Сообщение, которое так и не прошло, остаётся `Sending`, а не получает
  `Failed` по ошибке.
- При переподключении все фреймы из `pending` отправляются заново, как сейчас
  (protocol.md, раздел 13).

Конверт не шифруется повторно, поэтому `seq` и шаг храповика не меняются, и
ничего не пропадает.

### 2. Порядок для одного получателя сохраняется
Если конверт одному получателю ждёт повтора, link задерживает следующие фреймы
этому же получателю в порядке `client_id`, пока тот конверт не получит
`Accepted`. Фреймы другим получателям идут дальше.

Чтобы порядок соблюдался, link держит на проводе не больше одного
неподтверждённого `Send` на получателя. Иначе фреймы, отправленные сразу за
отклонённым, relay мог бы принять раньше него, если лимит успел пополниться.
Цена: одна задержка туда-обратно на каждое сообщение одному получателю. Файлы
и так идут по одному куску в 3 с (ADR-017).

Причин две:

- Куски файла принимаются только по порядку (`take_chunk`).
- vodozemac хранит не больше 40 пропущенных ключей на цепочку приёма
  (`MAX_MESSAGE_KEYS`). Конверт, который обогнали больше 40 более поздних в той
  же цепочке, расшифровать уже нельзя.

### 3. Постоянный отказ: ошибка для всего сообщения
`UnknownRecipient`, `Banned`, `TooLarge` и `Malformed` переводят сообщение в
`Failed`, как сейчас. Для кусков файла engine запоминает, к какому файлу
относится `client_id` каждого куска. Отклонённый кусок переводит весь файл в
`Failed` и останавливает отправку остальных кусков. Сейчас такой отказ
пропадает.

## Не новый протокол (правило 1)

Формат на проводе, relay и криптография не меняются. После отказа клиент
отправляет те же байты ещё раз, как он уже делает после переподключения.

## Метаданные, честно

Relay видит каждый повтор как ещё один `Send` тех же байтов от того же ключа,
через несколько секунд или минут. То же он уже узнаёт из повторной отправки
после переподключения. Новой информации с устройства не уходит.

## Что остаётся

- `pending` хранится в памяти. Отправка, которую relay ещё не подтвердил к
  моменту выхода из приложения (например, когда Android убивает его в фоне),
  становится `Failed: not confirmed before exit` и оставляет пропуск, как
  сейчас. Хранение `pending` на диске закрыло бы этот случай. Это отдельное
  решение, потому что тогда файл состояния будет содержать исходящий
  шифртекст.
- Relay по-прежнему может выбросить конверт из очереди (истёк срок в 14 дней,
  бан, нечестный relay). Получатель увидит пропуск: ради этого и нужен `seq`.
- Повтор не помогает против очереди, которая никогда не освобождается.
  Сообщение остаётся `Sending`, и это правда.

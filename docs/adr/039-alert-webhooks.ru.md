# ADR-039: приёмник вебхуков для алертов мониторинга

Статус: **предложено** (2026-11-22), ждёт решения владельца. English version: [039-alert-webhooks.md](039-alert-webhooks.md). Пересматривает пункт «Отклонено: TCP-порт на localhost» из [ADR-029](029-daemon.ru.md).

## Контекст

Мониторинг у команд уже есть: Prometheus с Alertmanager, Grafana, Uptime Kuma, Gatus. Их алерты уходят в Telegram-ботов, Slack или почту, то есть текст каждого инцидента проходит через третью сторону. termchat уже умеет слать из скриптов (ADR-024), через daemon (ADR-029), контакту или в приватную группу (ADR-033). Не хватает двери, в которую эти инструменты стучатся: они говорят только HTTP-вебхуками. Скрипт-прослойка работает, но каждая команда пишет свой и ошибается в кавычках, повторах и лимитах размера.

ADR-029 отклонил TCP-порт, потому что к нему может подключиться любой локальный пользователь. Вебхуку порт нужен, поэтому этот ADR должен ответить на это возражение.

## Решение

### 1. `termchat hook`

```
termchat hook --listen 127.0.0.1:9099 --token-file /etc/termchat/hook-token \
    --route ops=group:Ops --route oncall=contact:alice
```

- Отдельная долгоживущая подкоманда рядом с daemon. В ней **нет ни пароля, ни ключей**: она разбирает запросы и передаёт их daemon через его Unix-сокет (ADR-029). Нет daemon — нет доставки: ответ `503`.
- `--listen` по умолчанию `127.0.0.1:9099`. Любой другой адрес задаётся явно, и команда предупреждает, что токен тогда идёт по сети открытым текстом, если перед ней нет TLS-прокси. Своего TLS нет: Caddy или nginx делают это лучше, как и для relay.
- **Маршруты задаются при запуске.** `POST /ops` идёт в приватную группу `Ops`, `POST /oncall` — контакту `alice`. Запрос не может назвать получателя, поэтому владелец токена пишет только туда. Контакты должны быть приняты и проверены, как в ADR-032; группы — наши (ADR-033). Неизвестный путь: `404`.
- **Токен:** каждый запрос несёт `Authorization: Bearer <token>`. Токен читается из файла (`0600`, не меньше 32 случайных байт в hex или base64, `termchat hook --new-token` создаёт его), сравнение за постоянное время (`subtle`). Нет или неверный: `401`, больше ничего. Это ответ на возражение ADR-029: другой локальный пользователь подключиться может, отправить — нет.

### 2. Что становится сообщением

Маршрут принимает один из форматов, `--route ops=group:Ops:alertmanager` (по умолчанию `auto`):

- `alertmanager`: JSON вебхука Alertmanager; такой же шлёт единый алертинг Grafana. Одно сообщение на запрос: `FIRING` или `RESOLVED`, затем по каждому алерту `alertname`, `instance` (если есть) и аннотация `summary` или `description`.
- `kuma`: JSON Uptime Kuma (`msg`).
- `text`: тело как обычный текст (Gatus и всё, что умеет шаблон тела).
- `auto`: Alertmanager, если `alerts` — массив, Kuma, если `msg` — строка, иначе текст.

Только обычный текст (правило 9): без разметки, ссылки остаются текстом. Управляющие символы убираются, как в `clean_text`. Не больше 10 алертов в сообщении, дальше «and N more»; не больше 4000 символов, обрезка по концу строки. Остальные метки не попадают в текст: в них часто внутренние имена хостов и IP, которым нечего делать в чате. Маршрут может назвать дополнительные: `--labels job,severity`.

### 3. Ответы и лимиты

- `200`, когда daemon передал сообщение relay (relay принял), поэтому повторы Alertmanager покрывают недоступность relay; `503`, если daemon не работает или отправка не удалась; `400`, если тело не в формате маршрута; `413` больше 1 МиБ.
- Не больше 16 соединений, 10 секунд на чтение заголовков и тела, только HTTP/1.1, без keep-alive дольше одного запроса.
- Не больше 30 сообщений в минуту на маршрут; сверх этого ответ `429`, и Alertmanager повторит позже. Склейка повторяющихся алертов — это ADR-040 и D3.3, не здесь.

### 4. Разбор и зависимости

HTTP через `hyper` 1.x с `hyper-util` и `http-body-util`, которые уже есть в сборке через Arti: в `Cargo.lock` нового крейта нет, только новые прямые зависимости клиента. JSON через `serde_json`, он уже используется. Своего разборщика HTTP нет. Превращение JSON в текст получает негативные тесты и цель для фаззинга (правило 4).

## Модель угроз

- **Токен — ключ только на отправку** в заданные маршруты. Утечка позволяет писать текст от имени серверной личности в эти чаты, и только: ни чтения, ни других получателей, ни контактов, ни команд серверу. Смена: заменить файл и перезапустить `hook`.
- **Текст алерта попадает в чат целиком.** Всё, что Alertmanager кладёт в аннотации, оказывается в зашифрованном чате, в истории на устройстве каждого участника. Документация советует не класть секреты в аннотации.
- **Другой локальный пользователь** может подключиться к порту; без токена получит `401`. Локальный пользователь, который может прочитать файл токена, может отправлять. Файл `0600`, принадлежит пользователю службы.
- **Прослушивание не на loopback** без TLS-прокси открывает токен в сети. Только явно, с предупреждением.
- **Для relay ничего нового:** тот же daemon, очереди и сообщения, что у `termchat send`.
- **Правило 15:** один маршрут — один контакт или одна приватная группа, их задаёт оператор. Без рассылок и публичных групп.

## Отклонено

- **Читать прямо из сокета daemon:** Alertmanager, Grafana и Kuma не умеют говорить с Unix-сокетом.
- **Получатель в URL или теле:** владелец токена мог бы писать любому контакту.
- **Встроенный TLS:** сертификаты и их продление — дело обратного прокси; ещё одно место для ошибки.
- **Свой разборщик HTTP:** поверхность атаки без выгоды, hyper уже здесь.

## Что меняется

- `client`: подкоманда `hook` (приём, проверка токена, маршруты, форматы); раздел «Алерты из вашего мониторинга» в руководстве по скриптам (EN/RU) с примерами Alertmanager, Grafana и Kuma и юнитом systemd; строка в модели угроз.
- `core`, `proto`, `relay`, `engine`: без изменений.

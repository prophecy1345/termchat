# ADR-023: анонимные очереди на relay

Статус: **принято** (владелец, 2026-11-16). English version: [023-anonymous-queues.md](023-anonymous-queues.md).

## Контекст

Relay сейчас знает граф общения ([модель угроз](../threat-model.ru.md), «Оператор relay» и «Частично защищаемся»):

- **отправителя**: каждое соединение проходит `Auth` ключом Ed25519 личности, и relay ставит `sender` в `Deliver` (протокол, раздел 5);
- **получателя**: `Envelope.recipient` — ключ Ed25519 получателя (раздел 6), а `ClaimKey` называет `target` (раздел 4);
- **время** каждого сообщения и каждого подключения.

Размер уже скрыт бакетами, IP — через Tor (ADR-004). Остаётся граф «кто кому пишет».

Инкогнито-контакты (ADR-014) дают контакту отдельную личность, но:

- включаются вручную для каждого контакта; у основной личности relay видит весь круг контактов;
- relay всё равно хранит ключ каждой личности и аутентифицирует отправителя.

Sealed sender отклонён в ADR-014 (раздел 5): после инкогнито он прячет мало, а защита от злоупотреблений без знания отправителя требует криптографии, которой нет в vodozemac.

Вопрос владельца: почему relay вообще должен знать, кто и с кем переписывается?

Ответ: передавать байты, не зная **времени**, relay не может. Пакет приходит и уходит в конкретный момент. Но знать, **чьи** это байты, ему не обязательно. Мессенджер SimpleX показывает, что relay может работать с одними анонимными очередями, без аккаунтов и без идентификаторов пользователей.

## Решение

### 1. Очередь вместо аккаунта

На relay нет аккаунтов. Есть очереди. У очереди:

- `recv_id`: 16 случайных байт. По нему владелец забирает сообщения.
- `send_id`: 16 случайных байт, другие. По нему пишут в очередь.
- `recv_token`: 32 случайных байта, секрет владельца очереди.

Relay связывает `send_id` и `recv_id` одной очереди. Он не хранит ни Identity, ни ключ Ed25519 пользователя. Два разных ID нужны, чтобы по проводу (если TLS сломан или терминируется у третьей стороны) нельзя было сопоставить запись и чтение.

```
C -> R  CreateQueue
R -> C  QueueCreated { recv_id, send_id, recv_token }
C -> R  DeleteQueue { recv_id, recv_token }
```

ID и токен генерирует relay: так клиент не может выбрать ID чужой очереди. Создание очередей ограничивается так же, как сейчас регистрация: по IP, а для onion — общим бюджетом (протокол, раздел 11).

### 2. Пара очередей на каждый контакт

Для каждого контакта у человека своя входящая очередь. Её `send_id` он передаёт собеседнику только внутри Olm, новым вариантом внутреннего сообщения:

```
Body::QueueOffer { relay_url: String, onion_url: Option<String>, send_id: [u8; 16] }
```

- Каждый пишет в очередь собеседника и читает из своей. Получается пара очередей, по одной на направление.
- Получатель знает, какой контакт пишет, по тому, в какую очередь пришло сообщение. Поле `sender` в `Deliver` убирается. Клиент ему и так не доверяет: отправителя подтверждают расшифровка и `Inner.sender` (протокол, раздел 7). Эти проверки остаются.
- `Envelope.recipient` убирается: адрес — это `send_id`. Получатель по-прежнему сверяет `Inner.recipient` со своим ключом.

### 3. Отправка без аутентификации

```
C -> R  Send { client_id, send_id, envelope }
R -> C  Accepted { client_id } | Error { client_id, code }
```

`Hello`, `Challenge` и `Auth` для отправки не нужны. Писать в очередь может тот, кто знает `send_id`. Его знает только собеседник, потому что ID передавался внутри шифртекста.

### 4. Подписка на свои очереди

```
C -> R  Subscribe { recv_id, recv_token }
R -> C  Subscribed { recv_id } | Error { code }
R -> C  Deliver { recv_id, relay_id, envelope }
C -> R  Ack { recv_id, relay_id }
```

Доставка и подтверждение работают как сейчас (ADR-007, ADR-020). Push (ADR-012) привязывается к очереди, а не к аккаунту: `SetPush { recv_id, recv_token, endpoint }`.

### 5. Очередь приглашения и prekeys

У приглашения своя очередь: в неё пишут незнакомцы.

```
Invite { version: 3, relay_url, onion_url, identity: Identity, invite_send_id: [u8; 16], code: [u8; 16] }
```

- Prekeys публикуются на очередь приглашения: `PublishKeys { recv_id, recv_token, one_time, fallback }`.
- Незнакомец забирает ключ по `send_id`: `ClaimKey { send_id }`. Подпись `SignedKey` он проверяет ключом из `identity` в приглашении, как сейчас.
- Первое сообщение (`ContactRequestV2` с кодом ADR-013) идёт в очередь приглашения. После принятия запроса стороны обмениваются `QueueOffer` и дальше общаются через пару очередей контакта.
- Чтобы отозвать приглашение, человек удаляет очередь приглашения и создаёт новую.

Relay видит, что в очередь приглашения пишут, но не знает, чья она и кто пишет.

### 6. Злоупотребления (ADR-006, ADR-007)

Что меняется:

- **Лимиты.** Лимиты по ключу (`Send`, кадры, новые получатели в сутки) заменяются лимитами по очереди и по соединению. Лимит «новых получателей в сутки» теряет смысл: relay не знает, кто отправитель.
- **Блокировка контакта** — удаление его входящей очереди. Это сильнее, чем сейчас: заблокированный больше не может положить в неё ни байта, и у получателя не тратится место в очереди.
- **Спам от незнакомцев** возможен только в очередь приглашения. Квота незнакомца из ADR-007 становится квотой очереди приглашения. Если через приглашение спамят, человек пересоздаёт очередь.
- **Исчерпание prekeys.** Лимит «`ClaimKey` к одной цели» считается по очереди приглашения. Лимит «`ClaimKey` от одного ключа» заменяется лимитом по соединению и IP.
- **Жалобы и бан (потеря).** Relay не знает ключа отправителя, поэтому забанить ключ нельзя. Жалоба по-прежнему уходит оператору с раскрытым текстом, но оператор может только ограничить соединение или IP, с которого пишут в очередь. Автоматический бан по K жалобам (ADR-006) убирается. Защита держится на приглашениях, блокировке (удалении очереди) и лимитах.

### 7. Изоляция соединений (главный компромисс)

Анонимность очередей ничего не даёт, если relay может связать их по соединению:

- одно соединение подписано на очереди A, B, C — значит, это один человек;
- то же соединение пишет в очереди X, Y — значит, этот человек общается с владельцами X и Y.

Так relay снова строит граф. Поэтому:

- **Изоляция по контакту (по умолчанию):** чтение своей очереди и запись в очередь собеседника для одного контакта идут через отдельное соединение и отдельную цепочку Tor. Цена — та же, что у инкогнито (ADR-014): соединение на контакт, батарея, время запуска.
- **Общее соединение:** дешевле. Relay видит «эти очереди принадлежат одному человеку», но не видит, кто на другом конце, пока собеседник тоже не изолирован. Без Tor все соединения связывает IP.

Решение владельца: по умолчанию изоляция по контакту. Общее соединение пользователь может выбрать в настройках.

### 8. Совместимость и миграция

- Протокол relay получает `version = 2`. **Версию 1 relay не поддерживает** (решение владельца): переходного периода нет. Relay с версией 2 отвечает старым клиентам `UnsupportedVersion`, и те показывают сообщение об обновлении (ADR-010).
- При обновлении relay стирает аккаунты, ключи, prekeys, push-адреса и очереди версии 1. Баны ключей теряют смысл и тоже стираются.
- **Существующие контакты обрываются.** Передать `QueueOffer` через relay версии 1 нельзя, потому что её больше нет. Чтобы продолжить общение, стороны заново обмениваются приглашениями версии 3.
  - Если новый запрос контакта приходит от того же Identity, что у уже сохранённого контакта, клиент привязывает его к этому контакту: история, ник и проверенный отпечаток сохраняются. Без этого человек видел бы дубликат.
  - Старые сессии Olm с этим контактом удаляются: новый обмен начинает новую сессию.
- Старые приглашения версий 1 и 2 не принимаются; клиент просит у собеседника новое.
- Это честно описывается в заметке к релизу: после обновления всем контактам нужно обменяться приглашениями заново.
- Новые варианты перечислений идут в конец, как в ADR-012.

## Что relay знает после изменения

| | Сейчас | После |
|---|---|---|
| Ключи пользователей | все | ни одного (кроме тех, кто ещё на версии 1) |
| Кто отправил | да | нет |
| Кому адресовано | ключ получателя | случайный ID очереди |
| Какие очереди принадлежат одному человеку | — | только по общему соединению, IP или времени |
| Время записи и чтения | да | да |
| Размер | до бакета | до бакета |
| IP | без Tor | без Tor |

## Метаданные, честно

После изменения остаётся:

- **Время.** Relay видит, когда в очередь записали и когда из неё прочитали. Совпадение по времени (сообщение в X, через секунду чтение из A) может связать очереди. Убрать это может только mixnet с фоновым трафиком; это по-прежнему в «не защищаемся».
- **Связь через соединение и IP**, если нет изоляции (раздел 7).
- **Размер** с точностью до бакета; документ (ADR-017) — серия сообщений по 16 КБ.
- **Pre-key сообщение** длиннее обычного; relay видит начало новой сессии в очереди.
- **Число очередей** у одного соединения говорит примерно о числе контактов, если соединение общее.

## Это не новый криптопротокол (правило 1)

- `recv_id`, `send_id` и `recv_token` — случайные байты, которые передаются поверх TLS (и внутри Olm для `send_id`). Новых комбинаций примитивов нет.
- Olm, vodozemac, подписи Identity и `SignedKey` не меняются.
- Relay хранит не `recv_token`, а его SHA-256 (решение владельца). Изъятая база не даёт читать и удалять очереди. Это обычное применение хеша, а не протокол. Сравнение — по хешу, за постоянное время. `sha2` уже есть в зависимостях `core`.

## Отклонено

- **Sealed sender с анонимными учётными данными** (как в Signal): для защиты от злоупотреблений нужны слепые подписи или анонимные токены. В vodozemac их нет, свои писать нельзя (правило 1).
- **Ротация ID, выведенных из общего секрета через KDF:** это комбинация примитивов в свой протокол (правило 1). Случайные ID и явный `QueueOffer` дают то же без новой криптографии.
- **Mixnet и фоновый трафик:** закрыли бы время, но стоят задержки, трафика и батареи. Слишком дорого для проекта сейчас.
- **Только инкогнито для всех контактов:** дешевле, потому что протокол не меняется. Но relay по-прежнему хранит ключи, аутентифицирует отправителя и видит пары. Остаётся запасным вариантом, если этот ADR не примут.
- **Private information retrieval** для чтения очередей: слишком тяжело по вычислениям и трафику.

## Решения владельца (2026-11-16)

1. **Изоляция:** по умолчанию соединение и цепочка Tor на каждый контакт (раздел 7).
2. **Токен:** relay хранит SHA-256 от `recv_token`.
3. **Версия 1:** не поддерживается ни дня. Существующие контакты обмениваются приглашениями заново (раздел 8).
4. **Обратная очередь на другом relay:** разрешена. `QueueOffer` несёт `relay_url`, и клиент держит соединения с каждым relay, где лежат очереди его контактов. Тогда ни один relay не видит обе стороны пары.
5. **Автоматический бан по жалобам:** убирается. Защита держится на приглашениях, удалении очереди и лимитах (раздел 6).

## Поправка от 2026-11-16 (владелец): prekeys контакта и инкогнито-профили

При планировании реализации нашлись два пробела.

### 1. Новая сессия с уже существующим контактом

Иногда новая сессия Olm нужна с контактом, который уже есть: например, после восстановления из бэкапа без сессий. Сейчас ключ для неё берётся через `ClaimKey { target }`. По разделу 5 prekeys лежат только на очереди приглашения, а её адрес у контакта может уже не действовать.

Публиковать один и тот же fallback key на всех очередях нельзя: relay свяжет очереди по одинаковым байтам ключа.

Решение:

- На каждую свою входящую очередь контакта клиент публикует **2 одноразовых ключа** (`PublishKeys { recv_id, recv_token, one_time, fallback: None }`). Одноразовые ключи все разные, поэтому связать по ним очереди нельзя.
- Fallback key публикуется только на очереди приглашения.
- Контакт забирает ключ через `ClaimKey { send_id }` по адресу нашей очереди, который он и так знает.
- Relay присылает `KeyCount` тому, кто подписан на очередь. Клиент дополняет ключи до 2.
- Если ключей нет, relay отвечает `NoKeys`, и контакт пробует позже. Перейти на fallback key в этой очереди нельзя.
- vodozemac 0.11 хранит до 5000 секретных одноразовых ключей и при переполнении стирает самые старые. Ключ очереди контакта, опубликованный давно, может пропасть. Тогда сессия на нём не создастся. Клиент, получив pre-key сообщение, которое не смог расшифровать, публикует на этой очереди новые ключи.

### 2. Инкогнито-профили (ADR-014)

После перехода на очереди профили больше ничего не прячут от relay: он и так не знает ключей, а каждый контакт получает своё соединение (раздел 7). Но профили по-прежнему прячут контакты друг от друга: у профиля свой ключ, свой ник и свой отпечаток.

Решение:

- Профили остаются как защита **от контактов**.
- Отдельного подключения к relay у профиля нет. Его очереди обслуживает то же соединение на контакт, что и у остальных контактов.
- `Unregister` профиля заменяется на `DeleteQueue` его очередей.
- Разделы ADR-014 о том, что видит relay, заменяются этим ADR. Раздел о контактах остаётся в силе.

## Поправка от 2026-11-16 (владелец): запросы без кода приглашения

ADR-013 разрешал запросы контакта без кода, пока владелец не выключит настройку «принимать запросы без кода приглашения»: так старые приглашения без кода продолжали работать. После перехода на очереди эта настройка потеряла смысл и стала дырой.

- **Смысл.** Приглашения версий 1 и 2 отклоняются (раздел 8). В приглашении версии 3 код есть всегда. Честный запрос без кода прийти не может.
- **Дыра.** Адрес очереди приглашения остаётся тем же, когда владелец обновляет публичное приглашение: меняется только код. Тот, у кого осталось старое публичное приглашение, мог бы прислать `ContactRequest` без кода в ту же очередь и обойти обновление, если настройка включена.

Решение:

- Запрос без кода (`ContactRequest` вместо `ContactRequestV2`) от незнакомца отклоняется всегда, молча, как любой запрос с неверным кодом.
- Настройка удалена из всех интерфейсов. На её место в настройках встала настройка «одно соединение для всех контактов» (решение 1).
- Уже знакомого контакта это не касается: его запрос из очереди приглашения присоединяется к существующему контакту без проверки кода (раздел 8).
- Поэтому обновления публичного приглашения теперь достаточно: старый код больше ничего не открывает, а без кода войти нельзя. Очередь приглашения при этом остаётся прежней.

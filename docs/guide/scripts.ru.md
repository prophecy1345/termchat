# Скрипты и серверы

English version: [scripts.md](scripts.md).

`termchat` без аргументов открывает экран чата. С командой он делает одно дело без экрана и завершается, поэтому скрипт, задача cron или сервер могут прислать вам сообщение со сквозным шифрованием или прочитать ваш ответ: «бэкап не прошёл» на телефоне, без Telegram-бота и без третьей стороны, которая это читает.

## Команды

| Команда | Что делает |
|---|---|
| `init --nickname NAME [--relay URL] [--onion URL] [--tor]` | создаёт личность |
| `invite` | печатает одноразовое приглашение |
| `add INVITE` | просит контакт; он принимает в своём приложении |
| `contacts` | имя, отпечаток и состояние, по строке на контакт |
| `groups [--json]` | ID и название, по строке на группу |
| `send CONTACT [TEXT] [--expires 5m]` | отправляет TEXT или stdin, если TEXT не указан; ждёт, пока сообщение окажется на relay |
| `send-file CONTACT PATH` | документ до 1 МиБ |
| `recv [--from C] [--wait S] [--follow] [--json] [--save-dir DIR]` | печатает новые сообщения и изменения, каждое один раз; файлы сохраняются только в `--save-dir` |
| `watch send WATCHER --every SECS` | шлёт скрытые пульсы сторожу (нужен daemon) |
| `watch monitor SERVER --notify OWNER --after SECS` | пишет OWNER, когда пульсы SERVER прекращаются (нужен daemon) |
| `run (--to C \| --group NAME \| --group-id ID) [--name L] [--lines N] [--failures-only] -- COMMAND` | запускает COMMAND и сообщает, чем она закончилась |
| `hook --token-file PATH --route NAME=contact:C \| group:G [...]` | принимает вебхуки мониторинга и передаёт их дальше (нужна служба; см. ниже) |
| `page --to C [--then C ...] [--key K] [--every 5m] [--escalate 15m] [--give-up 2h] TEXT` | вызывает проверенный контакт, пока кто-то не ответит `ack КОД`, потом следующего (нужна служба) |
| `resolve --key K` | завершает вызов и сообщает всем вызванным, что проблема решена |
| `ask CONTACT QUESTION [--timeout SECS или Nm]` | ждёт подтверждения или отказа от проверенного контакта (нужен daemon) |
| `daemon` | держит личность открытой, и команды выше работают без пароля и отвечают сразу (Linux, macOS; см. ниже) |

Команды, которые открывают личность, принимают `--password-file PATH` или `--password-stdin` и `--timeout SECS` (по умолчанию 60). Папка состояния — `TERMCHAT_HOME` или `~/.termchat`.

- `CONTACT` — имя, которое показывает приложение, или начало отпечатка. Если подходит больше одного контакта, ничего не отправляется.
- **Пароль никогда не берётся из переменных окружения**: их наследует каждый дочерний процесс. Используйте файл, который принадлежит вам и имеет права `600`, stdin или клавиатуру. Без них termchat спрашивает пароль с клавиатуры, а у скрипта её нет: он завершится с «no terminal to type the password».
- Отправки «всем» нет: одна команда — один контакт.
- Запросы контакта принимает владелец в интерфейсе приложения. У CLI и daemon команды принятия нет.
- Текст собеседника очищается от управляющих символов, прежде чем попасть в ваш терминал или лог. Файлы сохраняются только в указанную папку и никогда не открываются.

**Сообщение, которое исчезнет.** `send --expires` даёт одному личному сообщению собственный таймер: `30s`, `5m`, `1h` или `1d`, от 10 секунд до 7 дней. Ваша копия исчезает через это время после отправки, а у получателя — через это время после того, как сообщение дошло до его устройства, как с таймером чата в приложениях. Секрет передавайте через stdin, чтобы он не попал в историю оболочки и список процессов:

```sh
printf '%s\n' "$DB_PASSWORD" | termchat send alice --expires 5m
```

Таймер ограничивает, сколько текст лежит в обоих чатах. От снимка экрана, уведомления на экране или копирования он не спасает. Сообщения в группе подчиняются таймеру группы, поэтому `--expires` работает только для контакта.

`send` и `send-file` ждут, пока relay примет сообщение, в пределах `--timeout`. Они возвращают `0`, если relay принял сообщение, `1` при ошибке пароля или состояния, `2` при неверных аргументах, `3`, если контакт не найден или неоднозначен, `4`, если сообщение ещё в очереди, и `5`, если его не удалось отправить.

## Приватные группы

Создавайте группы, принимайте приглашения и управляйте составом в приложении. Сервер может участвовать со своей личностью. Команда `groups` показывает доступные ей группы. Скопируйте ID, если названия совпадают или могут измениться.

```sh
termchat groups --json
printf '%s\n' 'Резервная копия готова' | termchat send --group 'Дежурство'
termchat recv --group-id 2b14b109d9b97317785a7bdb7075ae53 --follow --json
```

`--group` принимает точное отображаемое название, а `--group-id` — полный ID из 32 шестнадцатеричных цифр. Если для того же `TERMCHAT_HOME` запущен daemon, команды выполняются через него. Иначе CLI открывает личность сам.

Групповой `send` принимает один аргумент с текстом или читает stdin. Код `0` означает приём этого текста на relay, `1` — внутреннюю ошибку или ошибку состояния, `2` — неверные аргументы, `3` — ненайденную или неоднозначную группу, `4` — истечение срока ожидания, `5` — окончательный отказ или потерю доступа. Текст из очереди может прийти после таймаута. Отправленный кадр может попасть на relay до того, как отправитель узнает об изменении состава.

Групповой `recv` принимает либо `--wait SECS`, либо `--follow`. Без них он печатает уже пришедшие тексты и завершается. Ожидание без сообщений заканчивается с кодом `0`, потеря доступа — с кодом `5`. Обычный `recv` читает личные чаты. В групповом режиме флаги `--from` и `--save-dir` недопустимы.

Строка JSON со списком содержит `id` и `name`. У сообщения есть `group_id`, `group`, `from`, `fingerprint`, `at` (время приёма в секундах Unix), `id`, `text` и `reply_to` при наличии ответа. Оба ID сообщений передаются строками. Читаются входящие тексты и ответы, принятые после обновления. Если текст исправили до выдачи, выводится его текущая версия. Старая история, документы и последующие изменения доступны в приложении. Свои, удалённые и истёкшие тексты пропускаются.

Daemon отдаёт порцию всем читателям, которые уже ждут сообщения этой группы. Буфер одного читателя вмещает до 64 записей. При переполнении чтение завершается с кодом `1`. Отметка о выдаче сохраняется до вывода, поэтому разрыв канала или сбой может прервать вывод после выдачи текста.

## Как завести сервер

Шаги для Linux с systemd, команды от root. Дайте серверу **отдельную личность**, никогда не основную: тот, кто получит root на этом сервере, прочитает всё, что эта личность отправляет и получает, и сможет писать от её имени.

```sh
# 1. termchat для всех пользователей сервера
curl -fsSL https://raw.githubusercontent.com/prophecy1345/termchat/main/scripts/install.sh | TERMCHAT_INSTALL_DIR=/usr/local/bin sh

# 2. системный пользователь, которому принадлежит только эта личность, её папка и пароль, читаемый только им
useradd --system --home-dir /var/lib/termchat-bot --shell /usr/sbin/nologin termchat-bot
install -d -o termchat-bot -g termchat-bot -m 700 /var/lib/termchat-bot /etc/termchat-bot
head -c 30 /dev/urandom | base64 | sudo -u termchat-bot sh -c 'umask 077; cat > /etc/termchat-bot/pw'

# короткое имя для следующих шагов
bot() { sudo -u termchat-bot env TERMCHAT_HOME=/var/lib/termchat-bot termchat "$@" --password-file /etc/termchat-bot/pw; }

# 3. личность; ник — то, что вы увидите в приложении
bot init --nickname backup-box

# 4. ваше приглашение: Ctrl+O в терминале, Invite в приложении для компьютера, Your invite на Android
bot add 'termchat:...'
```

5. Примите запрос от `backup-box` в своём приложении.
6. Посмотрите, под каким именем сервер знает вас, и отправьте пробное сообщение:

```sh
bot contacts
bot send alice "привет от $(hostname)"
```

## Из systemd или cron

Служба или задача cron не видит того, что вы задали в своей оболочке: передайте ей `TERMCHAT_HOME` и файл пароля сами.

```ini
# /etc/systemd/system/disk-report.service
[Service]
Type=oneshot
User=termchat-bot
Environment=TERMCHAT_HOME=/var/lib/termchat-bot
ExecStart=/bin/sh -c 'df -h / | /usr/local/bin/termchat send alice --password-file /etc/termchat-bot/pw'
```

Для расписания добавьте `.timer`. С cron — `crontab -u termchat-bot -e`:

```
0 9 * * * TERMCHAT_HOME=/var/lib/termchat-bot /usr/local/bin/termchat send alice "доброе утро" --password-file /etc/termchat-bot/pw
```

`LoadCredential=` из systemd не подходит: копия, которую он делает, принадлежит root, а termchat принимает только файл пароля своего пользователя.

Одна личность выполняет одну команду за раз: вторая в тот же момент завершится с кодом 1 и скажет, что личность открыта в другом месте. Служба снимает это ограничение.

## Служба для бота, который отвечает

Каждая команда выше заново расшифровывает личность и подключается к relay: через Tor это 10–30 секунд на команду. `termchat daemon` делает это один раз и остаётся (ADR-029). Пока она работает, `send`, `send-file`, `recv`, `groups`, `contacts`, `invite` и `add` для того же `TERMCHAT_HOME` идут через неё: без пароля, с ответом за секунду и по нескольку сразу. `run` проверяет получателя и отправляет отчёт через неё. Если службы нет, всё работает как раньше. `watch` и `ask` работают только через неё.

```ini
# /etc/systemd/system/termchat-daemon.service
[Unit]
Description=termchat daemon
After=network-online.target
Wants=network-online.target

[Service]
User=termchat-bot
Environment=TERMCHAT_HOME=/var/lib/termchat-bot
ExecStart=/usr/local/bin/termchat daemon --password-file /etc/termchat-bot/pw
Restart=on-failure
NoNewPrivileges=yes
ProtectSystem=strict
ReadWritePaths=/var/lib/termchat-bot
PrivateTmp=yes

[Install]
WantedBy=multi-user.target
```

Бот, который отвечает на «status» и «disk» с телефона (`jq` разбирает JSON):

```sh
export TERMCHAT_HOME=/var/lib/termchat-bot
termchat recv --from alice --follow --json | while read -r line; do
  case "$(printf '%s' "$line" | jq -r .text)" in
    status) termchat send alice "$(uptime)" ;;
    disk)   termchat send alice "$(df -h / | tail -1)" ;;
  esac
done
```

- Служба слушает `daemon.sock` в папке состояния с правами `600` и пускает только своего пользователя. В сети ничего не слушает.
- **Пока она работает, пароль и ключи у неё в памяти, и любой процесс этого пользователя может писать через неё.** Давайте ей серверную личность под отдельным пользователем, никогда не основную.
- Отправляемый документ читает команда, а не служба; папка для `recv --save-dir` должна существовать заранее.
- Останавливается по SIGTERM или Ctrl+C: до 5 с ждёт, пока relay примет только что отправленное, потом сохраняет. На Windows службы нет.

## Получить сообщение, когда сервер замолчит

Заведите отдельные личности на двух хостах по шагам 1–3 из раздела «Как завести сервер». Назовём наблюдаемый сервер `backup-box`, сторожа `watcher`, а получателя тревог `alice`. Используйте `bot` из того же раздела на каждом хосте.

1. На хосте `watcher` выполните `bot invite` и скопируйте всю строку `termchat:…`. На `backup-box` выполните `bot add 'termchat:…'`, подставив эту строку.
2. Если daemon уже работает, остановите его на каждом хосте на время настройки. Для unit-файла из примера подойдёт `sudo systemctl stop termchat-daemon`. Откройте `termchat` без подкоманды от того же пользователя и с тем же `TERMCHAT_HOME`, что у службы.

   ```sh
   sudo -u termchat-bot env TERMCHAT_HOME=/var/lib/termchat-bot termchat
   ```

   Введите пароль служебной личности на каждом хосте.

3. В интерфейсе `watcher` выберите запрос от `backup-box` и нажмите **Ctrl+Y**. После принятия обе личности появятся друг у друга в контактах. На каждом хосте выберите этот контакт, откройте номер безопасности через **Ctrl+F**, сравните номера и при совпадении нажмите **v** на обоих хостах.
4. На `watcher` нажмите **Ctrl+A**, вставьте приглашение владельца и нажмите **Enter**. Владелец принимает запрос в своём приложении. Сравните номер безопасности с владельцем и отметьте его контакт как проверенный на `watcher`. [Как принимать запросы и сверять номера безопасности](contacts.ru.md)

Закройте оба терминальных интерфейса и запустите `termchat daemon` для каждой личности. Команды наблюдения запускайте от того же пользователя, с тем же `TERMCHAT_HOME` и с именами из `bot contacts` на соответствующем хосте.

```sh
# На наблюдаемом сервере, с TERMCHAT_HOME серверной личности
termchat watch send watcher --every 300

# На втором хосте, с TERMCHAT_HOME личности сторожа
termchat watch monitor backup-box --notify alice --after 900
```

В примере сервер шлёт пульс раз в пять минут, а сторож пишет после 15 минут тишины. Указывайте интервалы в секундах: `--every` не меньше 10, `--after` не меньше 30. Ставьте `--after` не меньше двух `--every` плюс минута на переподключение. Если порог не больше интервала отправки, сторож будет поднимать тревогу почти после каждого пульса. Обе команды работают на переднем плане. Запускайте их через менеджер служб, чтобы они перезапускались после остановки daemon или разрыва сокета. Пульсы скрыты из истории и `recv`, тревога приходит обычным личным сообщением, например «backup-box has been silent for 15 minutes».

Юнит для отправителя, рядом с юнитом daemon из раздела выше. Юнит для `watch monitor` на хосте сторожа отличается только `ExecStart`.

```ini
# /etc/systemd/system/termchat-watch.service
[Unit]
Description=termchat heartbeat to the watcher
After=termchat-daemon.service
BindsTo=termchat-daemon.service

[Service]
User=termchat-bot
Environment=TERMCHAT_HOME=/var/lib/termchat-bot
ExecStart=/usr/local/bin/termchat watch send watcher --every 300
Restart=always
RestartSec=10

[Install]
WantedBy=termchat-daemon.service
```

Включите его командой `systemctl enable --now termchat-watch`. Он запускается и останавливается вместе с daemon. Пока сокет daemon не появился, команда завершается, и systemd запускает её снова через 10 секунд.

Держите сторожа включённым и синхронизируйте часы. Сбой relay может вызвать тревогу или помешать её доставке. Daemon пишет в локальный журнал, когда ставит тревогу в очередь и когда не может подтвердить доставку. Свежий пульс позволяет сторожу сообщить о следующем сбое.

## Запросить подтверждение перед шагом скрипта

Заведите серверную личность и добавьте контакт, как в разделе «Как завести сервер». Отметьте контакт как проверенный на сервере по шагам 2 и 3 предыдущего раздела: остановите daemon, откройте `termchat` от пользователя службы, нажмите **Ctrl+F** на контакте, [сверьте номера безопасности](contacts.ru.md) и нажмите **v**. Затем снова запустите `termchat daemon`. На Linux и macOS запускайте `ask` от того же пользователя с тем же `TERMCHAT_HOME`.

```sh
if termchat ask alice "Выложить сборку 42 на staging?" --timeout 10m; then
    ./deploy-staging build-42
fi
```

На основном устройстве Алиса увидит обычное сообщение с двумя вариантами ответа, например `yes f4bc2801e9029d71` и `no f4bc2801e9029d71`. Она отправляет одну из этих строк. Регистр букв и пробелы по краям не важны, а лишние слова не допускаются. Сервер ждёт ответ с текущим кодом от её проверенного основного устройства. Ответ с привязанного компьютера не считается. Для каждого контакта можно ждать ответ на один запрос за раз. Таймаут по умолчанию — 10 минут. Значения `600` и `10m` равнозначны.

Если вопрос начинается с `--`, передайте его после разделителя `--`, а параметры укажите перед разделителем.

Команда ничего не печатает в stdout. Код `0` означает подтверждение, `1` — отказ, `4` — таймаут. Остальные ошибки используют `2` для неверных аргументов, `3` для неизвестного или неоднозначного контакта, `5` для неподходящего контакта, уже открытого запроса или ошибки отправки, `6` при недоступном daemon или внутренней ошибке. Задержавшийся вопрос может прийти после закрытия запроса. Ответ на него уже ничего не меняет.

Любой, кто может отправить сообщение с основного устройства Алисы, в том числе получивший её разблокированный телефон, может одобрить действующий запрос. Вопрос и ответ могут появиться в истории чата и уведомлениях, а вопрос — ещё и в истории оболочки или логах CI. Не включайте в вопрос секреты.

## Сообщить, чем закончилась команда

`termchat run` оборачивает команду. Когда она завершается, приходит одно сообщение: результат, длительность, хост и последние строки вывода (ADR-035).

```sh
termchat run --to alice --name nightly-backup --failures-only -- /usr/local/bin/backup.sh --full
```

```
nightly-backup failed with exit 1 after 42m 10s on backup-box
rsync: write failed on "/mnt/backup/db.tar": No space left on device (28)
```

- Выберите одного получателя: `--to CONTACT`, `--group NAME` или `--group-id ID`. termchat проверяет его до запуска команды. Неверный пароль, неизвестный контакт или недоступная серверу группа останавливают `run`, и команда не запускается.
- Всё после `--` — команда. termchat запускает её без оболочки. Для конвейера напишите `sh -c '…'` сами.
- В отчёте задача называется по `--name` или по имени файла программы. Аргументы и окружение в него не попадают.
- `--lines N` хранит от 0 до 50 строк, по умолчанию 10. Каждая строка обрезается до 500 байт. `--failures-only` ничего не шлёт, если команда завершилась с кодом `0`.
- Вывод команды по-прежнему приходит в ваш терминал или лог без изменений. Ей остаются stdin и окружение.
- Без daemon `run` нужен `--password-file`: личность открывается только для проверки и отправки, а не на всё время работы команды. `--password-stdin` не принимается, потому что stdin принадлежит команде.
- `run` выходит с кодом команды: её кодом, `128 + N`, если её остановил сигнал N, или `127`, если она не запустилась. Ctrl+C и SIGTERM достаются команде, а `run` всё равно присылает отчёт. Если команда успешна, а отчёт не ушёл, `run` возвращает код отправки (`1`, `4` или `5`). О проблеме с отправкой он всегда пишет в stderr.

В выводе могут оказаться секреты: токен, пароль, закрытый путь. Отчёт остаётся в истории чата и уведомлениях, а в группе — на каждом устройстве. Для таких команд используйте `--lines 0` или `--failures-only`.

## Алерты из вашего мониторинга

`termchat hook` принимает вебхуки от Alertmanager, Grafana, Uptime Kuma, Gatus и всего, что умеет POST, и передаёт каждый зашифрованным сообщением контакту или в приватную группу (ADR-039). Пароля и ключей у него нет: каждое сообщение он отдаёт [службе](#служба-для-бота-который-отвечает), поэтому сначала запустите её.

```sh
termchat hook --new-token /etc/termchat/hook-token     # один раз: 32 случайных байта, права 600
termchat hook --token-file /etc/termchat/hook-token \
    --route oncall=contact:alice --route ops=group:Ops --labels job,severity
```

- Маршрут — это `NAME=contact:CONTACT`, `NAME=group:GROUP`, `NAME=group-id:ID` или `NAME=page:CONTACT,CONTACT[:15m]` (см. [Вызов дежурного](#вызов-дежурного)), с форматом в конце по желанию: `:alertmanager`, `:kuma`, `:text` или `:auto` (по умолчанию, различает их сам). Тогда `POST /oncall` идёт alice, `POST /ops` — в группу. Запрос не может выбрать получателя.
- Контакт должен быть принят и с проверенным номером безопасности; `hook` проверяет каждый маршрут при запуске и иначе не стартует.
- Каждый запрос должен нести `Authorization: Bearer <токен>`. Без него: `401`.
- Слушает `127.0.0.1:9099`. `--listen ADDR` задаёт другой адрес; всё, кроме loopback, передаёт токен открытым текстом, поэтому ставьте перед ним TLS-прокси (Caddy, nginx).
- Алерт Alertmanager или Grafana становится строкой `FIRING (2)` и строкой на каждый алерт: имя, `instance` и аннотация `summary` или `description`. Другие метки не попадают в текст, если их не назвать в `--labels`: в них часто внутренние адреса.
- Ответы: `200`, когда relay принял сообщение, `503`, если нет службы или relay (Alertmanager повторит), `400` для тела не в формате маршрута, `413` больше 1 МиБ, `429` больше 30 сообщений в минуту на маршрут.

Alertmanager, в `alertmanager.yml`:

```yaml
receivers:
  - name: termchat
    webhook_configs:
      - url: http://127.0.0.1:9099/oncall
        http_config:
          authorization:
            credentials_file: /etc/termchat/hook-token
```

Grafana: точка контакта типа Webhook с этим URL и токеном в учётных данных «Authorization header» (схема `Bearer`). Uptime Kuma: уведомление Webhook с «Request Body» «Preset - application/json» и заголовком `{"Authorization": "Bearer <токен>"}`.

Юнит рядом с юнитом службы:

```ini
[Unit]
Description=termchat webhooks
After=termchat-daemon.service
Requires=termchat-daemon.service

[Service]
User=termchat-bot
Environment=TERMCHAT_HOME=/var/lib/termchat-bot
ExecStart=/usr/local/bin/termchat hook --token-file /etc/termchat/hook-token --route oncall=contact:alice
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

Текст алерта попадает в историю чата на каждом устройстве, которое его получает. Не кладите секреты в аннотации. Владелец токена может писать в маршруты, и только: ни чтения, ни других получателей, ни команд серверу. Чтобы сменить токен, замените файл и перезапустите `hook`.

## Вызов дежурного

`termchat page` вызывает, пока человек не ответит, а потом сообщает всем (ADR-040). Нужна служба.

```sh
termchat page --to alice --then bob --every 5m --escalate 15m --key disk-web1 \
    "Disk 95% full on web-1"
```

- alice получает текст со строкой `Reply "ack 3f9c2e81a07d6b54" to acknowledge.` Она отвечает ровно этим с основного устройства, в приложении или через `termchat send`.
- До ответа она получает напоминание каждые `--every` (по умолчанию 5m, не меньше 1m). Через `--escalate` (по умолчанию 15m) вызывается и bob, со своим кодом, а alice получает «Passed to bob». Подтвердить может любой из них; остальные узнают, кто это сделал.
- `page` выходит с `0`, когда вызов подтвердили, с `4`, когда никто не ответил до `--give-up` (по умолчанию 2h, не больше 7d) или вызов раньше разрешили, с `3` для неизвестного контакта, с `5`, если контакт не проверен, с `6` без службы.
- `--key` даёт имя инциденту. Второй `page` с открытым ключом никого заново не вызывает: он шлёт «Still firing (2)». `termchat resolve --key disk-web1` завершает вызов и шлёт «Resolved after 14m».
- Каждый контакт цепочки должен быть принят и проверен. Вызовы идут только контактам, не в группы. Они живут в памяти службы: перезапуск службы их сбрасывает.

Из приёмника вебхуков маршрут может вызывать вместо отправки: `--route oncall=page:alice,bob:15m`. Сработавший алерт Alertmanager открывает вызов с ключом по его fingerprint, тот же алерт в статусе resolved его разрешает; монитор Uptime Kuma, упавший, вызывает, поднявшийся — разрешает.

Подтверждение только останавливает напоминания. Оно ничего не разрешает на сервере, и ничто из присланного контактом не может запустить там команду.

## Свой ИИ-бот

Внутри termchat нет ИИ, и ничего из написанного вами не попадает в модель, если вы сами её туда не отправите. Если ИИ нужен, запустите его как отдельный контакт: [`deploy/ai-bot/termchat-ai-bot`](https://github.com/prophecy1345/termchat/blob/main/deploy/ai-bot/termchat-ai-bot) отвечает на каждое сообщение языковой моделью, рядом со [службой](#служба-для-бота-который-отвечает) на вашей машине.

Он работает с любым API чата, совместимым с OpenAI. По умолчанию это [Ollama](https://ollama.com) на той же машине, так что весь путь остаётся вашим:

```sh
ollama pull llama3.2
AI_ALLOW="12345 67890 11121 31415 16171 81920" termchat-ai-bot
```

- `AI_ALLOW` — отпечатки тех, кому можно пользоваться ботом, через запятую; остальных он не замечает.
- `AI_URL` (по умолчанию `http://127.0.0.1:11434/v1`), `AI_MODEL` (по умолчанию `llama3.2`), `AI_KEY_FILE` (файл с правами `0600`) или `AI_KEY` для API с ключом, `AI_SYSTEM` для системной подсказки.
- Каждое сообщение отвечается отдельно: историю разговора бот не хранит.
- Нужны `jq` и `curl`; ответ уходит через `termchat send`, поэтому служба должна работать.

Юнит рядом с юнитом службы:

```ini
[Unit]
Description=termchat AI bot
After=termchat-daemon.service
Requires=termchat-daemon.service

[Service]
User=termchat-bot
Environment=TERMCHAT_HOME=/var/lib/termchat-bot
Environment=AI_ALLOW=12345 67890 11121 31415 16171 81920
ExecStart=/usr/local/bin/termchat-ai-bot
# Always: it may start before the daemon's socket is up, and then ends cleanly.
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target
```

С удалённым API вместо локальной модели всё, что вы пишете боту, уходит этому провайдеру, и для него это открытый текст: шифрование кончается на вашем сервере. Не добавляйте бота в группу: он передал бы всё, что говорят в группе. Ключ API держите в файле с правами `0600`, а не в юните.

## Из GitHub Actions или другого CI

Не храните личность termchat в секретах CI (ADR-036). Секрет — неизменная копия личности, и каждый запуск начинал бы с того же состояния шифрования и повторял бы ключи сообщений. Вместо этого CI подключается по SSH к серверу, где работает личность для CI, ключом, который может только писать одному контакту.

```sh
# на сервере от root: пользователь с оболочкой, потому что sshd запускает принудительную команду через неё
useradd --system --create-home --home-dir /var/lib/termchat-ci --shell /bin/sh termchat-ci
usermod -p '*' termchat-ci          # без входа по паролю, но не заблокированная учётная запись
chmod 700 /var/lib/termchat-ci
install -d -o termchat-ci -g termchat-ci -m 700 /etc/termchat-ci /var/lib/termchat-ci/.ssh
head -c 30 /dev/urandom | base64 | sudo -u termchat-ci sh -c 'umask 077; cat > /etc/termchat-ci/pw'
ci() { sudo -u termchat-ci env TERMCHAT_HOME=/var/lib/termchat-ci termchat "$@" --password-file /etc/termchat-ci/pw; }
ci init --nickname ci-example
ci add 'termchat:...'               # ваше приглашение; примите запрос в приложении

# на вашем компьютере: ключ только для этого репозитория
ssh-keygen -t ed25519 -N '' -f termchat-ci -C 'ci example/repo'

# на сервере: этот ключ может только писать alice
printf 'command="TERMCHAT_HOME=/var/lib/termchat-ci /usr/local/bin/termchat send alice",restrict %s\n' \
  "$(cat termchat-ci.pub)" >> /var/lib/termchat-ci/.ssh/authorized_keys
chown termchat-ci: /var/lib/termchat-ci/.ssh/authorized_keys; chmod 600 /var/lib/termchat-ci/.ssh/authorized_keys
```

Запустите `termchat daemon` для этого пользователя, как в разделе «Служба для бота, который отвечает», с `User=termchat-ci` и его путями. Проверьте, что `ci contacts` показывает `alice` в состоянии `ok`. Если в `sshd_config` есть `AllowUsers`, добавьте туда `termchat-ci`.

В настройках репозитория сохраните закрытый ключ `termchat-ci` как секрет `TERMCHAT_SSH_KEY`. Ключ хоста сервера сохраните как переменную `TERMCHAT_HOST_KEY` одной строкой, например `ci.example.org ssh-ed25519 AAAA…`. Берите его из `/etc/ssh/ssh_host_ed25519_key.pub` на самом сервере, а не из сети. Затем добавьте этот шаг в конец задачи:

```yaml
      - name: Report to termchat
        if: always()
        env:
          KEY: ${{ secrets.TERMCHAT_SSH_KEY }}
          HOST_KEY: ${{ vars.TERMCHAT_HOST_KEY }}
          TEXT: "${{ github.repository }} ${{ github.workflow }} #${{ github.run_number }}: ${{ job.status }} ${{ github.server_url }}/${{ github.repository }}/actions/runs/${{ github.run_id }}"
        run: |
          umask 077
          printf '%s\n' "$KEY" > "$RUNNER_TEMP/termchat-key"
          printf '%s\n' "$HOST_KEY" > "$RUNNER_TEMP/termchat-host"
          printf '%s\n' "$TEXT" | ssh -T -i "$RUNNER_TEMP/termchat-key" -o IdentitiesOnly=yes \
            -o BatchMode=yes -o StrictHostKeyChecking=yes \
            -o UserKnownHostsFile="$RUNNER_TEMP/termchat-host" termchat-ci@ci.example.org
```

- sshd запускает только принудительную команду, что бы ни просил клиент. Текст приходит через stdin, получатель задан на сервере.
- Шаг завершается с кодом `send`, например `4`, если сообщение ещё в очереди.
- `restrict` запрещает проброс портов, агента и X11 и терминал. Утёкший ключ может только слать тексты `alice` от имени `ci-example`. Чтобы отозвать его, замените его строку в `authorized_keys`.
- Значения из `github` идут через `env`, а не прямо в `run`: имя ветки или сообщение коммита может выбрать любой, у кого есть право push.

**Подтверждение перед выкладкой.** Создайте второй ключ и привяжите его к заданному вопросу. Сначала отметьте `alice` проверенной для личности CI, как в разделе «Запросить подтверждение перед шагом скрипта».

```sh
printf 'command="TERMCHAT_HOME=/var/lib/termchat-ci /usr/local/bin/termchat ask alice \\"Deploy example/repo to production?\\" --timeout 30m",restrict %s\n' \
  "$(cat termchat-deploy.pub)" >> /var/lib/termchat-ci/.ssh/authorized_keys
```

Используйте тот же шаг с этим ключом, `< /dev/null` вместо текста и `timeout-minutes: 35`. ssh возвращает код выхода удалённой команды, поэтому задача продолжается только после `yes`: `1` значит отказ, `4` — время вышло.

## Ещё примеры

```sh
# конец долгой команды, на ноутбуке (опять отдельная личность)
make release; termchat send alice "сборка релиза: код $?" --password-file ~/.termchat-bot.pw

# текст из пайпа
df -h / | termchat send alice --password-file /etc/termchat-bot/pw

# ждать ответа до 10 минут, строками JSON
termchat recv --from alice --wait 600 --json --password-file /etc/termchat-bot/pw
```

## Что печатает recv

Обычный вывод: `alice: текст`, `alice edited: текст`, `alice deleted a message`, `alice reacted like to: текст`.

С `--json` — один объект на строку:

```json
{"at":1794913363,"fingerprint":"78125 66938 20371 20023 95579 06120","from":"alice·78125","id":"17037012887881307594","kind":"react","mine":true,"reaction":"love"}
{"at":1794913393,"fingerprint":"78125 66938 20371 20023 95579 06120","from":"alice·78125","id":"5136533931879411279","kind":"message","reply_to":{"id":"5235206626092912747","mine":true},"text":"which disk? / or /var?"}
```

- `kind`: `message`, `edit`, `delete` или `react`.
- `id`: сообщение, строкой (числа больше 2^53 читатели JSON искажают). Для `react` поле `mine` говорит, ваше ли это сообщение; `reaction` — одно из `like`, `love`, `laugh`, `wow`, `sad`, `thanks`, `dislike` или `null`, если реакцию убрали.
- `reply_to`: на что отвечает сообщение; `mine` там говорит, было ли оно вашим.
- `at`: когда пришло само сообщение.

Сообщение, исправленное до того, как `recv` его забрал, приходит один раз, уже в новом виде; удалённое до этого не приходит вовсе.
